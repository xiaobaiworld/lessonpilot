# D-V1-032：视觉设计系统作为 UI 开发标准

- 日期：2026-09-01
- 状态：已接受
- 范围：KnownMap 四端 UI 的设计、实现、评审和验收

## 要解决的问题

阶段 0 已建立视觉方案、token 生成链路和共享消费入口，但如果只把方案当作一次改版说明，后续页面仍可能重新按各端习惯分叉。项目需要一个长期有效、可被后续 Agent 和开发者直接检索的 UI 参考依据。

## 已确认事实与约束

- 当前视觉方向 A「纸绿收敛」已经通过示意图对比和人工确认。
- [`doc/design/v1/11-visual-design-system.md`](../design/v1/11-visual-design-system.md) 已记录色彩角色、字阶、间距、表面层级、四端收敛方式和实施门禁。
- `v1/assets/brand/knownmap-tokens.json` 与生成的 `tokens.css` 已建立真源和消费链路。
- 视觉标准不能改变已冻结的页面职责、交互状态机、数据契约、权限和失败恢复规则。

## 考虑过的方案

1. 只保留为本次视觉改版的参考稿：改动范围小，但后续开发没有统一依据，容易再次漂移。
2. 另建一份更短的 UI 规范：查找更快，但会复制视觉真源，产生第二套取值和解释。
3. 保留 11 号设计文档作为唯一视觉真源，并在项目开发规则和文档入口中声明其为强制参考：不复制内容，后续实现直接回链原文。

## 决定

采用方案 3。以后所有新增或修改的 Web、销售站点、管理端和学生插件 UI，开工前都要以 11 号视觉设计系统为主要参考；涉及颜色、字体、间距、圆角、阴影、动效或页面层级时，优先使用其角色 token 和消费入口。若需求确实需要偏离，必须在对应设计/决策文档中说明原因、影响和验证方式，不能在代码里静默另立一套视觉语言。

## 重新讨论条件

- 品牌方向、目标用户、平台约束或长期使用舒适度发生变化；
- 11 号设计系统与已验证的可访问性、浏览器能力或产品需求发生冲突；
- 四端出现新的表面类型，现有 token 角色无法表达且需要新增设计语言。

## 影响

- `doc/dev-rules.md` 将 11 号设计系统列为项目级 UI 标准和开发真源。
- `doc/INDEX.md` 与 `doc/design/v1/README.md` 保留可检索入口；11 号文档继续保存完整视觉决策，不另建复制版。
- 以后 UI 功能的计划、实现、截图验收和代码评审都应回链 11 号文档；现有历史裸色值仍按 `D-V1-031` 分阶段清零。
