# 教师平台本地开发切片决策

- 日期：2026-08-18
- 状态：已接受，部分验证。教师侧节点 1–7 已验证；插件侧节点 8 和完整闭环节点 9 待实现
- 依据：`doc/AI_Learning_Companion_Product_Function_Spec_v0.2.md`
- 关联需求：`doc/requirements/teacher-platform-local-stage.md`

## 1. 要解决的问题

第一阶段已经完成销售页和产品原型 Demo。下一阶段需要把现有教师界面接入真实的教师发布能力和插件课程下载能力，但暂时不需要完整的学生平台。

如果直接按 v0.2 全量实现，会同时引入学生身份、授权领取记录、学习数据、教师报表、管理员后台和公网部署，超过当前开发测试闭环的验证需要。

## 2. 已确认事实

- 当前教师端界面已经存在，当前工作重点是补齐后端和配套功能。
- 需要采用 FastAPI 风格的后端 API 节点。
- 当前先在本地构建和运行，未来要能够迁移到公网。
- 本地数据库采用 SQLite。
- 教师账号由开发者手工预建几个测试账号。
- 教师使用登录名和密码登录。
- 当前一个课程只有一个课节，但数据模型保留后续多个课节能力。
- 当前先支持重点内容、选择题、填空题和问答题四种节点。
- 授权码只需要绑定课程并让插件下载对应已发布课程配置。
- 学生只能通过 KnownMap 提供的解压版 Chrome 插件访问课程。
- 不开发独立学生网页。
- 不开发 Chrome Web Store 分发。
- 当前不实现学生身份、领取记录、学习数据和复杂授权状态。

## 3. 考虑过的范围

### 方案 A：直接实现 v0.2 的完整平台

收益：

- 直接覆盖完整产品规格。

成本和风险：

- 需要同时设计学生身份、授权来源并集、数据上传、报表、管理员后台和公网运行环境；
- 会把当前验证目标从“教师发布并让学生取得课程”扩大成完整 SaaS；
- 交付周期、测试面和数据迁移风险明显增加。

### 方案 B：教师发布 + 授权码下载的本地开发切片

收益：

- 能验证当前最关键的教师使用和学生取得课程路径；
- 只引入当前必要的账号、课程、脚本、授权码和插件下载接口；
- SQLite 便于本地重建，FastAPI API 保留未来公网部署边界；
- 后续学生数据可以在稳定的课程和授权模型上继续扩展。

成本和风险：

- 当前不能证明完整学生管理和学习数据闭环；
- 授权码没有完整撤销、过期、人数和身份语义；
- 需要在界面和文档中明确这是开发测试阶段能力。

## 4. 决定

采用方案 B。

当前系统的最小后端闭环为：

```text
教师登录
→ 课程/课节/脚本草稿
→ 发布课程
→ 创建授权码
→ 插件提交授权码
→ 返回已发布 PluginCourseConfig
```

授权码当前是课程下载凭证，不是学生身份，也不创建领取记录。

## 5. 实现影响

- 新增本地 FastAPI 服务、SQLite 数据库、初始化/迁移和测试配置。
- 教师前端通过 API 读取和写入课程，而不是继续把保存结果只放在页面状态。
- 现有 `src/shared/course-contract.js` 继续作为插件课程输出契约的基础；服务端使用独立的领域模型，并通过适配器生成插件配置。
- 插件将在节点 8 增加授权码输入和课程下载流程，并继续使用现有 B 站原页面宿主。
- 生产部署、公网域名、TLS 和监控平台不进入本阶段代码交付，但配置和 API 不得依赖本机绝对路径。

## 7. 假设和重开条件

假设：

- 第一批测试教师可以接受手工提供账号和手工安装解压版插件。
- 一个课程一个课节足以验证当前教师发布流程。
- 四种节点足以作为第一版脚本契约；新增节点时扩展节点注册表和 schema。
- 本地 SQLite 的数据量满足当前开发测试。

重开条件：

- 教师测试必须由管理员自助创建账号；
- 学生必须在没有插件的网页中学习；
- 授权码必须具备撤销、过期、人数或身份限制；
- 课程需要同时管理多个课节才能完成真实试用；
- 学习数据成为当前测试的必要结果；
- 本地 SQLite 无法支持实际测试并发或数据保留要求。
