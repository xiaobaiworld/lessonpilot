# D-V1-028：埋点采用自有事件契约、Umami 老师端适配与项目日志规范

- 日期：2026-09-01
- 状态：已接受，待需求/设计专项审核与实现验证
- 决策编号：`D-V1-028`
- 关联计划：[`AI Learning Companion 埋点模块计划`](../plans/2026-09-01-ai-learning-companion-instrumentation.md)

## 1. 要解决的问题

AI Learning Companion 需要知道老师在哪些课程制作、预览、发布和授权环节遇到阻塞，也需要为后续学生学习指标保留可解释的事件结构。当前项目没有统一的行为事件契约，也不能因为接入分析工具就突破学生学习数据的本机边界。

## 2. 已确认事实与约束

1. 当前 v1 不自动上传学生课程、回答、结果、进度或可还原这些内容的数据。
2. 学生插件运行在 B 站页面环境中，不能记录无关浏览历史，也不应把宿主页面交给会话回放平台。
3. 当前项目已使用 AJV 校验 JSON Schema；跨边界契约由仓库内版本化 Schema 作为真源。
4. 老师 Web 与学生插件是不同的数据主体和运行边界；教师业务真源仍是服务端课程、发布和授权数据。
5. 当前阶段不建设大规模数据仓库、全链路追踪或复杂告警系统。
6. Umami v3 提供自托管、显式自定义事件、Funnels、Retention、Boards 和 Session Replay；Replay 自 v3.1 起提供，但仍需显式开启和配置遮罩。
7. 项目已有 `structlog`、请求级 `request_id`、日志级别配置和敏感字段脱敏；关键动作需遵守 `OBSERVABILITY_STANDARD.md` 与 `DEV-LOG-001`。

## 3. 考虑过的方案

### 方案 A：直接把 OpenReplay 作为全端埋点平台

- 收益：回放、前端错误、网络信息和事件较完整。
- 成本/风险：自托管依赖较多；学生端回放容易触及字幕、回答、B 站页面和本机隐私；事件 Schema 与业务指标定义仍需自行维护。
- 结论：不采用为当前全端方案；保留为老师端调试工具备选。

### 方案 B：Umami 作为老师端分析适配器，自有 Schema 作为事件真源，并复用项目日志规范

- 收益：自托管相对简单；支持事件属性、漏斗、留存和 Dashboard；仓库可以只依赖轻量 Tracker；事件平台可替换；技术日志继续由现有 `structlog` 和 `request_id` 提供。
- 成本/风险：Umami 不是服务端业务真源；身份、事件字段和学生端本地导出仍需自行定义；Replay 需要额外审查。
- 结论：采用。

### 方案 C：自建完整事件仓库和 Dashboard

- 收益：权限、指标、数据生命周期完全由项目控制。
- 成本/风险：需要新增服务端接收、存储、查询、聚合、权限、导出、保留和运维能力，超过当前“不要太投入时间”的目标。
- 结论：当前不采用；只有在教师报表、跨设备同步或正式远程学习档案成立后重开。

## 4. 决定

1. 事件定义使用项目自有的版本化 JSON Schema、事件注册表和 `track()` 封装，不把 Umami 字段直接当作业务真源。
2. v0.1 只把 Umami 用于教师 Web 的显式产品事件和可选 UX 回放；关闭自动采集，不接入 B 站宿主页和学生内容脚本。
3. 老师课程、发布、授权等事实指标仍从现有服务端权威数据派生；Umami 只用于行为路径、阻塞点和界面体验分析。
4. 学生端只记录有限学习检查点到本机，原始回答、字幕全文、课程正文和全量播放器/UI 事件不进入通用埋点；远程同步或主动导出需另立需求和隐私边界。
5. AI/LLM 调用的延迟、错误、Token 和成本未来使用 OpenTelemetry 侧的运行指标，不混入老师/学生行为事件。
6. 产品分析事件与技术诊断日志并行建设、明确分工：事件进入 Umami/Mock，日志进入现有 `structlog` 输出；同一 API 动作用内部 `request_id`/`event_id` 关联，但不把高基数关联字段作为 Umami 分析属性。
7. 关键动作统一覆盖日志 `start`、`success`、`failure`、`retry`；日志不记录密码、会话、授权码、课程正文、字幕、学生回答或学习状态。

## 5. 依赖的假设与重开条件

### 假设

- 已有或可以提供一台满足 Umami 官方最低要求的自托管环境；否则先只实现本地事件契约和 Mock 适配器。
- 老师端事件属性可以只使用课程、课节、发布版本和非个人化的稳定 ID，不发送账号、联系方式或课程正文。

### 重开条件

- 需要远程教师学生报表、跨设备学习档案或自动回传学生学习数据；
- Umami 自托管实际维护成本超过当前阶段可接受范围；
- 需要跨多个产品、仓库或下游工具路由事件；
- 需要 AI 调用链路、采样、告警或合规审计达到独立可观测性平台规模。

## 6. 影响范围

- 计划：新增 `doc/plans/2026-09-01-ai-learning-companion-instrumentation.md`。
- 契约：新增分析事件 Schema、版本登记和事件注册表；不修改课程包 Schema。
- Web：新增教师端显式事件封装和 Umami 配置开关。
- 插件：后续只新增本地有限学习检查点时才修改插件；修改插件必须递增 `EXTENSION_VERSION`。
- 后端：本计划第一阶段不新增埋点接收端点，不改变现有业务事务和权威数据模型。
- 日志：复用 `v1/backend/app/infrastructure/logging/`，必要时新增动作封装和测试，不新建集中日志平台。
- 文档：需求、设计和追踪矩阵需在实现前补充正式的埋点条目；本决策和计划先作为开发前置依据。
