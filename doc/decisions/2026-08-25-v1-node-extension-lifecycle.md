# D-V1-013：新增课程节点统一生命周期与接口边界

日期：2026-08-25

状态：已接受

相关文档：[`../design/v1/10-node-extension-standard.md`](../design/v1/10-node-extension-standard.md)

## 1. 要解决的问题

后续课程会继续增加节点。若每次只在教师页面、学生运行时或后端 Schema 中临时增加一个分支，
节点的显示、学生动作、返回值、本地记录、发布包和版本迁移容易出现不一致。项目需要一套
在设计阶段就能检查完整性的固定流程，并明确什么时候需要后端专用接口。

## 2. 已确认事实和约束

- v1 已有四类基线节点：重点内容、选择题、填空题和问答题。
- 每个课节使用一个当前脚本草稿；草稿按整份聚合保存并经过服务端 Schema 校验。
- 课程发布生成不可变课程快照，学生端从课程包读取已发布节点。
- 学生回答、尝试、节点结果和进度当前属于学生本机数据，不上传服务端。
- 节点需要稳定身份、触发规则、类型专属字段、完成规则和状态兼容信息。
- `FR-AUTHOR-011` 已要求所有节点类型遵守统一生命周期，新增标准需要把这条要求落为可执行清单。

## 3. 考虑过的方案

### 方案 A：每种节点各自设计一套接口和生命周期

优点是单个节点可以快速定制；缺点是会重复实现权限、草稿、发布、课程包、日志、错误和版本迁移，
容易让不同节点的行为和数据边界漂移。放弃。

### 方案 B：所有节点使用统一公共契约，只有确有服务端职责时增加专用接口

节点统一经过身份、编辑、草稿、预览、发布、课程包、运行和本地状态流程；普通节点复用现有草稿和
课程发布边界，服务端计算、外部数据或跨设备业务才单独设计接口。采用。

### 方案 C：节点完全只在前端实现，后端只保存任意 JSON

前端迭代较快，但服务端无法可靠校验、发布和拒绝未知结构，课程包和不同运行时之间也无法共享确定契约。
与现有封闭 Schema、发布快照和权限边界冲突。放弃。

## 4. 决策

采用方案 B：

1. 每个新增节点先填写节点定义卡，明确类型、显示、学生动作、返回值、完成规则、播放器行为、
   本地记录、后端职责和兼容键；
2. 普通节点复用现有课节草稿读取/保存、真实预览、课程发布和课程包交付接口；
3. 学生运行结果继续由本机学习状态承载，除非另行接受服务端数据、隐私和保留需求；
4. 节点只有在需要服务端持久化、服务端计算、权限范围数据、异步外部服务或跨设备事实时，才设计专用 API；
5. 未知类型和不兼容版本必须显式降级或拒绝，不得静默当作其它类型执行；
6. `stateCompatibilityKey` 是节点状态迁移的必要依据，节点 ID 相同不能单独证明语义兼容。

## 5. 影响

### 需求

- `FR-AUTHOR-011` 的统一节点生命周期要求获得具体执行入口；
- 后续新增节点必须把显示、返回、本地记录和后端职责作为同一需求评审；
- 如果新增节点需要服务端学习数据或教师报表，必须重新打开相关数据、隐私和报告范围。

### 设计与接口

- 新增 [`10-node-extension-standard.md`](../design/v1/10-node-extension-standard.md) 作为节点扩展标准；
- 草稿和发布接口继续承载普通节点；
- 专用节点 API 必须另行定义完整请求、响应、错误、幂等和安全契约；
- 节点类型、课程包和本机存储版本需要在实现时同步更新支持矩阵。

### 测试与发布

- 新节点必须通过契约、教师编辑、后端草稿、真实预览、课程包、学生运行、本地恢复和版本迁移测试；
- 只有真实预览和发布包安装验证通过，节点才能进入正式课程；
- 未知类型、不兼容状态和部分失败属于必测异常路径。

## 6. 依赖假设与重开条件

当前决策依赖以下事实：

- v1 学生学习状态继续保持本机边界；
- 当前草稿和课程发布仍以整份聚合为主要保存与交付单位；
- 节点没有独立的跨课程查询、服务端评分或教师学习报表需求。

出现以下情况时必须重开本决策：

- 需要教师查看学生回答、尝试、完成情况或节点级统计；
- 节点需要服务端异步计算、外部数据或跨设备连续性；
- 课程包不再能承载节点运行所需的完整内容；
- 需要局部节点并发编辑或独立发布；
- 现有本机学习状态无法表达新节点的返回值、完成状态或迁移语义。

## 7. 后续行动

- 将节点标准登记到 v1 设计索引；
- 在接口契约和数据流文档中建立回链；
- 下一次新增节点时以定义卡作为设计评审输入；
- 若新增节点引入新的重要数据或服务端能力，先新增或替代决策记录，再实施代码。
