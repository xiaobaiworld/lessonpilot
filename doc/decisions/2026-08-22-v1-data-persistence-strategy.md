# D-V1-011：v1 数据持久化策略

日期：2026-08-22

状态：已接受，待 v1 实施验证

## 问题与边界

v1 需要冻结脚本/发布内容的物理存储方式，以及学生本机学习记录的事实粒度。这两项会影响数据库结构、Chrome 存储、迁移和测试，但不扩大已冻结的产品范围。

## 已确认事实与约束

- v1 只有四类基线节点，它们随课节脚本整体保存、校验、预览和发布；
- 当前没有跨课程按题型查询、服务端评分或节点级并发编辑需求；
- 学生学习数据只在本机保存，必须区分未提交草稿、正式尝试、当前结果和派生进度；
- v1 不上传学习数据，不建设教师报表，也不要求回放全部播放器和 UI 历史；
- 当前草稿 `config_json` 和课程包已验证聚合契约可行，但 v1 必须补齐统一 Schema、修订、摘要和读写双重校验。

## 考虑过的方案

### 脚本与发布内容

1. **聚合 JSON**：每个课节草稿和发布课节快照保存版本化 JSON，由共享 JSON Schema 校验。
2. **节点关系表**：把节点公共字段和各类型内容拆成多张表，通过联接重建草稿和发布快照。

关系表能加强节点字段的数据库约束和查询，但会增加表、联接、类型迁移和不可变快照的复杂度。当前没有对应业务收益。

### 学生本机学习记录

1. **当前状态 + 追加式正式尝试**：继续位置、输入草稿和节点结果保存当前值；每次正式提交追加不可变尝试；进度重算。
2. **全量事件溯源**：保存播放、窗口、输入和节点的全部事件，通过重放恢复当前状态。

全量事件可提供更强回放能力，但会扩大本机数据、隐私、迁移和损坏恢复成本，并且没有 v1 用户可见需求。

## 决定

1. 脚本草稿使用经版本化 JSON Schema 校验的聚合 JSON；发布使用 `CourseRelease + ReleaseLessonSnapshot` 不可变聚合快照，不把四类节点拆成多张专用表。
2. 学生本机学习记录使用“当前状态 + 追加式 `NodeAttempt`”；进度从当前发布范围和学习事实重算，不保存全量事件日志。

## 理由、代价与可逆性

该方案直接对应当前的原子保存、课程级发布、契约共享和单机学习边界，能以更少表和更少本机数据完成必要验收。代价是 SQLite 不能单独约束 JSON 内的每个节点字段，也不能从事件从零回放全部 UI 历史；必须依靠共享 Schema、读写校验、契约测试和局部恢复保证完整性。

聚合 JSON 可以通过版本化迁移转为关系模型，正式尝试也为未来扩展分析保留了可验证事实；但两种转换都需要显式迁移，不是无成本切换。

## 假设、重开条件与影响

当前假设是 v1 不需要大量服务端节点查询、节点级多人并发编辑、全量学习行为回放或学习事件上传。出现以下任一情况时重开：

- 服务端需要按节点类型、题目或内容字段做高频跨课程查询；
- 脚本出现真实的节点级多人并发编辑或独立生命周期；
- 经审核的教师报表、跨设备同步或法定审计确实需要更细学习事件；
- 真实容量、迁移或损坏恢复证据证明当前聚合成为主要瓶颈。

影响范围：04 固定数据边界；05 定义状态变化和恢复；06 定义 JSON Schema 及插件契约；09 定义旧 `config_json`、`PublishedScript` 和 `studentCourseStore` 迁移；测试计划必须覆盖 Schema 双向校验、不可变快照、尝试幂等、进度重算和局部损坏。
