# D-V1-018：教师工作台按课程版本管理发布与授权

- 日期：2026-08-27
- 状态：已接受；后端端点变更已批准并进入实现
- 决策编号：`D-V1-018`
- 替代范围：替代现有需求与设计中“多个发布版本仍属于同一门课程、发布后继续保留原草稿、课程级授权自动跟随后续发布”的表述；不替代 `D-V1-015` 的授权码使用数量限制。

## 1. 要解决的问题

教师工作台需要让教师明确区分“正在制作的课程”和“已经交付的课程版本”。发布、修改本版本、增加版本和生成授权码必须有可理解且不混淆的对象边界。当前文档把发布版本建模为同一 `Course` 下的历史版本，无法表达本次确认的产品规则。

## 2. 已确认事实

1. 工作台名称改为“互动课程制作”。
2. 页面说明文字固定为：“为视频课程增加互动能力，视频学习过程中加入互动环节，让学习更有趣，提升课程价值。”
3. 草稿卡片中的课程标题区域也可以进入修改页面，行为与“继续制作/修改课程”相同。
4. 点击“发布课程”时，系统根据当前已确认的草稿内容创建一个新版本；发布后该草稿不再保留。
5. 不同版本的课程视为不同课程，具有不同的课程身份。它们可以通过后续的升级关系建立关联，但不能只靠标题、视频或版本号猜测关联。
6. 每个已发布课程版本都可以单独生成授权码；授权码只针对点击时选中的课程版本。

## 3. 决策

### 3.1 草稿发布

教师在草稿区点击“发布课程”后：

1. 按当前已保存且通过发布校验的内容创建一个新的已发布课程版本；
2. 为这个已发布版本分配独立课程身份，并记录其版本/来源关系；
3. 发布成功后，把新课程版本放入“已发布”区域；
4. 消耗当前草稿，不在“草稿”区域继续保留同一份草稿；
5. 发布失败、冲突或结果未知时，不删除当前草稿，也不产生半个已发布课程。

### 3.2 已发布版本的两个编辑动作

对已发布区域中的某个课程版本提供两个互斥语义不同的操作：

- **修改本版本**：把选中的已发布课程版本退回草稿区供教师修改，同时移除该版本在已发布区域的课程记录。这个版本作为已发布课程不再保留；后续重新发布时生成新的课程版本。
- **增加版本**：以选中的已发布课程版本为内容基础创建一份新的草稿，原已发布课程版本继续保留在已发布区域；新草稿完成发布后，再形成一个新的独立课程版本。

上述动作不能静默互换。页面必须在确认前显示目标版本、草稿变化和“原发布版本是否保留”的影响。

### 3.3 当前课程级授权码管理（按 `D-V1-019` 实现）

已发布区域的每个课程卡片都进入该 `course_id` 的授权码管理页。当前阶段按
[`D-V1-019`](2026-08-27-course-access-latest-release.md) 执行：授权码绑定 `course_id`，兑换或更新时自动解析该课程最新可交付版本；不新增 `release_id` 绑定。

当前管理能力包括：

- 单个或一次 1–100 个批量生成授权码；
- 查看该课程已分发授权码的完整码、状态、领取设备数、首次和最近领取时间；
- 数据库不保存授权码明文，服务端用受保护密钥和生成意图确定性重建，并只向所属教师返回；
- 终止授权来源继续沿用既有端点和资格重算规则。

未来恢复真正的版本级授权时，才按以下规则扩展：

- 授权范围的根对象是当前选中的已发布课程版本；
- 授权码不能默认指向同名课程、课程族或其它版本；
- 授权记录、课程列表和操作审计都必须能回溯到具体课程版本；
- 授权码的发布版本绑定必须在服务端校验，不能由前端自行选择或推断。

## 4. 下一步记录但本次不开发

为了支持版本之间的升级，需要后续定义并实现“课程族/升级关系”能力：教师可以选择原来的课程版本升级到新的课程版本。这里的“同一个课程”只表示版本之间存在业务关联，不改变“不同版本是不同课程”的身份规则。

原先记录的课程升级兼容方向仍属于后续设计；当前同一 `course_id` 的有效课程级授权已经会自动取得该课程最新可交付版本，
不把它扩展解释为跨独立课程升级。以下内容本次只记录，不开发：

- 旧授权码如何识别可升级的新课程版本；
- 教师如何配置或变更版本升级关系；
- 学生端如何展示升级提示、确认更新和处理本机学习状态；
- 旧版本授权码、课程版本、授权范围和更新资格的兼容校验；
- 旧授权码是否跨越课程族边界，以及版本删除/归档后的更新行为。

在上述能力完成前，新生成的授权码只绑定创建时选择的 `course_id`；服务端在兑换/更新时解析最新可交付 `CourseRelease`。
不得声称已经支持独立课程之间的升级关系或版本级授权。

## 5. 影响范围

- 需求：新增教师工作台课程版本管理、版本级授权码和后续升级兼容边界；修订原“历史发布版本属于同一课程”的需求。
- 数据：已发布课程版本需要独立课程身份，并保留可审计的版本来源/升级关系信息；草稿、已发布课程和授权码的生命周期必须分开表达。
- 交互：工作台标题、说明文字、课程标题点击、草稿发布和已发布版本操作按钮按本决策实现。
- 接口：新增原子版本草稿端点和授权码批量创建端点；授权查询扩展完整码与领取使用摘要。授权目标仍复用 `course_id` 和最新发布版本查询。

## 6. 后端端点可组合性审计（2026-08-27）

在进入实现前检查了当前 `v1` 后端路由、应用服务、模型、Schema、OpenAPI 路径和相关自动化测试。
结论是：页面文案、标题点击等展示行为可以由前端独立完成；核心业务不能只用现有端点组合完成。

1. `POST /api/v1/teacher/courses/{course_id}/releases` 当前在同一 `course_id` 下递增 `release_number`，且发布服务不消费 `ScriptDraft`，不能满足“不同版本是不同课程”和“原草稿不保留”。
2. `GET /api/v1/teacher/courses` 以 `course_id` 聚合课程，只返回最新发布指标，不能直接返回按独立课程版本拆分的已发布区域。
3. 现有课程文件导出/导入和课程归档端点不能安全组合成“修改本版本/增加版本”的原子业务动作，不能用前端多次请求替代。
4. `POST /api/v1/teacher/access-codes` 的 `GrantItem` 只保存 `course_id`，`effective_grants` 和课程更新也按 `course_id` 聚合；这正好满足当前“课程授权自动解析最新可交付版本”的决定，不满足未来版本级授权。
5. `POST /api/v1/student/course-updates` 当前取课程的最新可交付发布版本；当前继续复用该行为，课程族、升级关系和跨独立课程兼容属于后续阶段。

产品负责人已批准补充后端业务端点。冻结后的实现边界如下：

1. `POST /api/v1/teacher/courses/{course_id}/version-drafts` 接收 `mode=modify|add` 和幂等键；`modify` 原子移除当前课程的发布快照并由快照重建草稿，`add` 保留原发布并创建新 `course_id` 草稿。
2. `POST /api/v1/teacher/access-codes/batch` 原子生成 1–100 个授权码；单个创建继续复用原端点。
3. `GET /api/v1/teacher/access-codes` 和明细响应对所属教师返回可恢复的完整码及领取使用摘要，不返回凭证摘要或本机标识摘要。
4. 前端只消费上述业务 DTO 和错误码，不承担最新版本判定、授权绑定、回滚或跨请求事务。

- 测试：覆盖修改本版本不保留发布、增加版本保留原发布、幂等重放、批量生成整体性、完整码归属隔离及失败不丢原内容。
- 迁移：为课程增加版本族/来源/业务版本号，并增加版本操作幂等记录；现有课程按自身 `course_id` 初始化为版本族第一版，不迁移学生本机数据。

## 6. 重新讨论条件

出现以下情况时重新审核：课程版本是否必须保留可见历史；教师是否需要恢复被“修改本版本”移除的发布内容；旧授权码升级是否需要教师逐个选择目标版本；或本机学习状态无法在版本间安全迁移。
