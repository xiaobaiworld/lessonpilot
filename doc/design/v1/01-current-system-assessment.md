# 01 当前系统与代码经验评估

文档版本：`1.0.1`

状态：已于 2026-08-22 通过人工审核；已补记 `D-V1-010` 暴露的现状差距；本文件不定义 v1 目标架构

评估日期：2026-08-22

需求真源：[`../../requirements/v1/README.md`](../../requirements/v1/README.md)

## 1. 目的与边界

本文件在 v1 目标设计之前回答四个问题：

1. 当前代码实际实现了什么；
2. 哪些行为经过自动化、人工或生产验证；
3. 哪些经验值得进入 v1 设计；
4. 哪些结构只是原型演化结果，不应默认继承。

当前代码是可执行的现状描述，但不是 v1 设计真源。旧设计能够解释代码为何演化到当前状态，
但较晚文件通常只修正局部，也不自动替代较早文件的全部内容。

本文件不决定最终模块划分、数据模型、接口形状、页面布局或代码复用比例。

## 2. 证据权重与冲突处理

整理 v1 设计时按以下权重使用证据：

| 顺序 | 证据 | 用途 |
| ---: | --- | --- |
| 1 | 已冻结 v1 需求与已接受决策 | 定义目标行为、范围和验收边界 |
| 2 | 可重复运行结果、人工验收与生产记录 | 证明技术事实、真实风险和已经验证的方法 |
| 3 | 当前代码、数据库迁移和配置 | 描述当前实现、数据形状和迁移负担 |
| 4 | 按时间与功能整理的旧设计演化链 | 解释方案理由、局部修正和历史取舍 |
| 5 | 未执行计划、界面文案和历史完成声明 | 只作为线索，不能单独证明能力存在 |

冻结需求权重最高，但不假定需求绝不会出错。若需求与已验证的技术事实、平台边界或安全事实冲突，
必须记录冲突并重新审核，不能静默修改需求，也不能用现有代码反向覆盖需求。

代码与旧设计冲突时，运行结果用于判断“当前实际上发生什么”；目标行为仍由冻结需求和后续已接受
设计决定。代码中方便但未经业务确认的选择，只视为实现偶然性。

## 3. 当前系统组成

当前仓库是一套在短期原型中连续叠加形成的单仓库系统：

| 组成 | 当前职责 | 主要事实 |
| --- | --- | --- |
| `teacher-web/` | 销售、示例、教师编辑、管理员和早期诊断页面 | 原生 HTML/CSS/JavaScript；多个历史页面并存 |
| `backend/` | 管理员、教师、课程、课节、草稿、发布和授权 API | FastAPI、SQLAlchemy、Alembic、SQLite |
| `src/` | Chrome MV3 插件、B 站运行时、本机课程库和旧预览桥 | 插件版本 `0.9.1`；学生课程库存储版本 `2` |
| `tools/` | 静态站和教师平台构建、部署、验证与回滚 | 两个发布脚本合计超过 1,500 行 |
| `deploy/` | Nginx、systemd、SQLite 备份和发布记录 | 当前生产目标为 knownmap.com 与阿里云 ECS |
| `tests/`、`backend/tests/` | Node、后端集成/单元和人工验证 | 自动化覆盖较多，真实 Chrome 闭环仍有未完成项 |

当前主要运行链路为：

```text
管理员创建教师与工作空间
  -> 教师登录并创建课程、课节和脚本草稿
  -> 教师发布课程包并创建授权码
  -> 插件用授权码下载课程包
  -> 插件把课程和学习状态保存到当前 Chrome
  -> B 站页面匹配课节并执行互动节点
```

这条链路已经证明产品方向的若干关键技术可行性，但并未完整实现冻结需求中的全部业务语义。

## 4. 当前能力与 v1 需求差距

### 4.1 身份、工作空间与管理

当前已经实现：

- 管理员与教师使用独立账号、Cookie 和会话表；
- 密码使用 Argon2 哈希，会话只保存 HMAC 摘要；
- 管理员可以查看、创建教师并重置密码；
- 创建教师时建立其唯一工作空间；
- 服务端按当前教师和工作空间过滤课程、课节与草稿。

主要差距：

- 没有完整的教师停用、恢复和相应会话终止路径；
- 管理页面主要覆盖账号创建与重置，不是完整的 v1 支持工作台；
- 管理员最小可见范围和高风险动作确认仍需按 `FR-WS-*`、`FR-ADMIN-*` 重新设计；
- 管理员和教师认证代码存在结构重复，是否复用应由新设计决定。

### 4.2 课程、课节与教师制作

后端已经具备 UUID 课程、多课节、有序课节、独立草稿和四类节点的基础数据链路。教师浏览器能够
本地解析 SRT/VTT，节点编辑器支持点击、拖放、键盘放置、移动、编辑和删除。

但当前教师页面仍是原型约束：

- 只读取课程列表中的第一门课程；
- 主要操作一门课程的一个课节；
- BVID、示例字幕和兜底时长写死为同一门面试课程；
- 缺少课程信息修改、归档、课节完整维护和视频引用更新；
- 草稿没有并发版本或冲突检测，后写入者可能覆盖先写入者；
- 教师旧版 JSON 课程文件导入导出已存在；`.kmcourse` 课程包及管理员代目标教师导入导出已按第 12 号设计新增，教师类型自助权限仍未开放。

因此后端“能够存多门课程和多个课节”不能表述为完整的教师多课程产品已经完成。

### 4.3 预览、发布与课程版本

当前发布会确认课程至少有一节课节，按已有草稿（没有草稿时使用空互动内容）生成发布快照，并保存发布结果；
测试预览是可选的制作辅助，不是发布门槛。草稿保存与发布动作分离，
已发布内容不会因后续草稿保存而直接改变。

当前模型仍有一个已确认的核心问题：发布版本按课节分别递增，但学生取得的是整门课程包；同一次发布
生成的完整课程包又分别存入多个课节快照。这不能准确表达 `FR-PUBLISH-005` 至
`FR-PUBLISH-010` 要求的课程级原子发布版本，也不具备明确的并发发布幂等语义。

早期 `currentCourse` 与 `activePreviewSession` 桥仍存在于插件中，但它服务于旧单课程教师预览，
不能作为 v1 真实预览设计直接继承。当前教师页面的“打开视频”也不等于已实现锁定草稿版本、隔离学生
状态的真实预览。

### 4.4 授权与领取

当前已经验证：

- 授权码使用高熵随机值，服务端只保存 HMAC 摘要和尾号；
- 原文只在创建响应中返回一次；
- 支持短期和长期领取窗口；
- `AccessGrant` 可以表达课程、课节、节点和有效时间范围；
- 下载时由服务端裁剪授权范围，插件不提交自选课程 ID；
- 无效、过期或无可用内容时不返回课程正文。

当前尚未完整实现：

- 用稳定本机学习标识建立可追溯领取关系；
- 多个授权来源的持久化并集和重复领取幂等；
- 教师永久终止一个授权来源的未来在线资格；
- 凭证领取窗口、持续在线资格和已安装本机内容三套生命周期；
- 教师端查看完整授权范围和资格状态。

当前代码把一次有效授权码下载近似为授权关系，这个简化不应进入 v1 数据模型。

### 4.5 学生课程库与运行时

插件已经实现 v2 多课程本机存储、课程包独立校验、失败不覆盖、并发下载串行化、同课程更新时迁移
可对应节点状态，以及 BVID 精确匹配和 B 站单页导航清理。

主要差距：

- 下载 API 仍固定为 `127.0.0.1:8000`，生产插件闭环未完成；
- 安装和更新前没有完整展示范围、版本及学习状态影响；
- 没有删除课程、重置进度和明确的存储损坏恢复流程；
- 当前课程包契约拒绝同一课程内重复 BVID，运行时也只取每门课程第一个匹配课节；`D-V1-010` 已允许
  同一或不同课程的多个课节复用同一视频，v1 必须返回全部合法候选；
- 多个课节匹配同一视频时，当前代码按来源、安装时间和课节顺序静默选择，而 v1 要求学生明确选择；
- 学习会话没有锁定课程发布版本，课程库更新可能改变后续运行依据；
- 真实 Chrome 下的授权、刷新、SPA、错误和日志边界验收仍有未执行项。

### 4.6 本机学习状态

当前本机状态按课程、课节和节点隔离，能够记录答案、尝试次数以及 `completed` 或 `retry`。更新课程时，
只保留仍能由稳定节点 ID 对应的状态。

当前状态不足以实现冻结需求：

- 没有独立的本机学习标识和学习会话；
- 没有继续位置、未提交输入草稿和幂等尝试标识；
- 节点状态过于简化，不能区分完整生命周期；
- 没有课节/课程进度重算、完成范围和显式重置；
- 开放问答当前直接视为正确，只能证明界面流程，不代表完整学习语义。

### 4.7 公开入口、部署与运维

公开销售页和飞书表单入口已实现，飞书链接使用 HTTPS 官方域名白名单并在无登录状态下验证过。
教师 Web、FastAPI、SQLite、Nginx、systemd、发布记录和回滚链路已经部署到阿里云 ECS。

发布过程具有值得保留的原则：精确 Git 提交、依赖锁定、白名单打包、SHA-256、不可变发布目录、
原子切换、上线探针、失败恢复和发布记录。

当前实现差距包括：

- 发布脚本体积很大且职责集中，测试主要验证脚本文本和有限构建行为；
- GitHub Pages 仍发布早期插件诊断页，是否继续公开应由 v1 发布边界决定；
- 当前备份配置保留 14 天，与 `D-V1-006` 已接受的 30 天目标不一致；
- 审计日志、诊断日志和试用申请的自动保留/删除策略尚未完整实现；
- 固定插件 ZIP 的生产下载、升级和回退尚缺完整真实 Chrome 验收。

## 5. 验证证据的真实含义

2026-08-22 在当前分支实测：

- `node --test tests/*.test.js`：331 项通过；
- Node 覆盖率：被纳入统计的文件行覆盖率约 79%；
- `cd backend && uv run pytest -q`：96 项通过；
- 后端应用行覆盖率约 95%；
- 仓库保存了 7 份状态为 `verified` 的生产发布记录。

这些数字不能直接表示“v1 已完成”：

- Node 测试包含大量静态页面结构、文案和历史兼容断言；
- 教师主应用、插件 service worker、B 站播放器接入和真实 DOM 运行没有被覆盖率完整统计；
- `admin.js` 与可视化编辑器的可执行行覆盖明显低于契约和纯函数模块；
- 早期消息桥、授权领取和 B 站运行的多项人工验收仍标记待执行；
- 后端测试覆盖较强，但测试的是当前数据模型，不能证明该模型满足新的课程级发布与授权关系语义；
- 后端当前产生 42 条依赖或运行时弃用警告，是版本升级时需要处理的兼容信号。

## 6. 值得继承的经验

以下内容应作为 v1 设计输入，而不是机械复制现有文件：

1. 所有外部课程包、文件、网页消息和插件响应均按不可信输入处理；
2. 共享契约只有一个实现真源，使用显式版本、封闭字段和稳定错误码；
3. 下载、安装、更新和迁移失败时保留最近有效数据，不留下半写入状态；
4. 管理员、教师、学生本机状态使用不同身份和权限边界；
5. 密码使用强哈希，Cookie/token/授权码原文不持久化、不进入日志；
6. 字幕默认只在教师浏览器解析，学生学习状态保持单机边界；
7. B 站页面只做精确匹配和最小播放器控制，页面生命周期变化必须清理旧状态；
8. 发布从精确提交构建，采用白名单、校验和、不可变目录、原子切换和可恢复验证；
9. 示例、测试数据和真实交付证据必须明确区分；
10. 自动化不能替代真实 Chrome、真实 B 站和真实发布路径的人工验收。

## 7. 不应默认继承的原型负担

以下结构只能作为迁移源或经验证据：

- 固定 BVID、固定 08:33 时长、内置面试字幕和示例课程；
- 教师页面只取第一门课程、一个课节的工作流；
- `currentCourse`、`activePreviewSession` 等旧单课程预览键；
- 课程包节点规则通过旧单课程契约的临时 envelope 复用；
- 每个课节保存一份完整课程包并分别递增发布版本；
- 用授权码下载记录近似持续授权关系；
- 多课程匹配时静默按排序选择；
- 示例页、销售页、诊断页、教师页和管理员入口的历史混排；
- 大型原生脚本、全局对象和单文件 CSS/HTML 的当前组织方式；
- 以脚本文本断言代替真实部署或浏览器行为的测试；
- 为旧原型入口长期保留公开权限或生产发布文件。

是否复用某段代码，应在其对应 v1 设计和迁移测试明确后逐项决定，不能按目录整体保留或整体推倒。

## 8. 对后续 v1 设计的约束

后续文档必须区分三种视角：

1. **当前系统评估**：本文件描述已经存在的代码、数据、证据和问题；
2. **v1 目标设计**：从冻结需求建立目标领域模型、架构、契约、交互、安全和运维；
3. **迁移与实施计划**：比较现状与目标后，决定保留、重写、迁移、拒绝或退役。

目标设计不得写成当前代码的整理版，也不得为了“推倒重来”丢弃已经验证的安全、数据和发布经验。
只有需求、目标设计和迁移结论都明确后，才决定具体代码复用比例和实施顺序。
