## 1. 目的

本目录在已冻结 v1 需求基础上，整理旧设计与当前代码经验，再建立 v1 目标设计、开发规范、
测试计划和实施计划。

旧文档全部进入审计范围，但旧内容不会整段复制到新文档。每项内容必须先判断其演化位置、
独有价值、冲突、验证证据和最终去向。

## 2. 权威顺序

解释冲突时使用以下顺序：

1. 已冻结 v1 需求和已接受产品决策；
2. 已通过人工审核的 v1 设计；
3. 可重复运行结果、真实人工验收和生产记录；
4. 当前代码和数据库迁移所描述的实现事实；
5. 已完成演化审计的旧设计、计划和研究资料；
6. 未执行计划、历史状态声明和示例文案。

需求、设计和代码均可能有错误。高权重内容若与已验证技术或安全事实冲突，必须重新审核，
不得静默选择其中一方。

## 4. 旧资料编号与审计方式

旧资料继续使用需求阶段已经建立的稳定编号 `SRC-001` 至 `SRC-082`，不再建立第二套来源编号。
原始来源清单见 [`../../requirements/v1/13-legacy-source-register.md`](../../requirements/v1/13-legacy-source-register.md)。

设计阶段在 `02-legacy-document-register.md` 中补充：

- 文件在时间和功能演化链中的位置；
- 仍然有效的独有内容；
- 已被需求、后续设计或代码事实替代的内容；
- 应进入的 v1 目标文档；
- 最终保留、归档、替换或拒绝结论。

同一文件可以同时包含应吸收、应保留为证据和应否决的片段。较晚文件只替代其明确修改的范围，
不因日期较新自动成为整份真源。

## 5. 人工审核与归档门禁

- 纯事实、重复、失效链接和已被冻结需求唯一决定的冲突由审计直接处理；
- 存在多个合理目标方案且会改变产品、数据或长期工程边界时，集中提交最多 5 项人工决策；
- 旧文件只有在独有内容已有去向、冲突有结论、新真源有回链且链接已更新后才能移出活跃区；
- 删除不是默认动作。失去当前指导价值的文件进入带来源日期的归档，测试和生产证据保留可追溯入口；
- 目标架构必须等全部旧文档完成审计后才开始定稿。
