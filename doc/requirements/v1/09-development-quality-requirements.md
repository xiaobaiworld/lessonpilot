## 1. 第一阶段质量目标

第一阶段的开发质量目标是：让每个已接受需求都能被准确实现、可重复验证、可安全修改并可以追溯，
不用文档数量、代码行数、测试数量或工具数量代替真实业务结果。

本文件只建立六类 `DEV-*` 门禁：

| 编号域 | 当前必要结果 |
| --- | --- |
| `DEV-STRUCT-*` | 代码、共享契约与模块责任不形成多个真源 |
| `DEV-DEP-*` | 依赖与环境配置可重现、可检查且不携带秘密 |
| `DEV-CODE-*` | 实现遵守已审核边界，错误不被静默掩盖 |
| `DEV-TEST-*` | 正常、失败和边界行为有可重复证据 |
| `DEV-LOG-*` | 关键业务动作能安全定位，不泄露秘密或学生本机数据 |
| `DEV-DOC-*` | 需求、决策、设计、代码、测试和实际状态保持同步 |

本阶段不为了“工程化”提前建设微服务、通用插件平台、复杂发布编排、全量设备实验室或大型质量平台。

## 2. 单条需求格式

每条正式 `DEV-*` 要求使用以下字段：

1. 状态；
2. 优先级；
3. 来源；
4. 质量要求；
5. 失败边界；
6. 验收证据；
7. 关联需求。

## 3. 工程结构与契约

#### DEV-STRUCT-001：每项共享规则只有一个实现真源

- 状态：已接受
- 优先级：P0
- 来源：Web、服务端和插件需要共享身份、课程、发布包、消息和版本语义
- 质量要求：源代码、测试和工程文档职责明确；同一契约或校验规则只维护一个权威实现，其它运行边界通过导入、生成或明确适配使用
- 失败边界：不用复制代码、隐式默认值或顺序依赖临时解决契约冲突；冲突未解决时不发布新契约
- 验收证据：目录职责检查、共享契约引用检查及 Web、服务端和插件契约一致性测试
- 关联需求：`DATA-QUALITY-001`、`INT-EXT-002`、`INT-PACKAGE-002`、`SEC-TRUST-001`、`SEC-TRUST-002`

#### DEV-STRUCT-002：对外契约变更同步版本和消费端

- 状态：已接受
- 优先级：P0
- 来源：API、数据库、课程发布包、教师课程文件和插件消息均会被其它模块或旧版本使用
- 质量要求：对外数据结构或行为变更时，同步更新契约版本、校验、必要迁移、消费端、测试和相关文档；不兼容变更必须可识别且安全拒绝旧数据
- 失败边界：不允许只改生产端或只改单个消费端；不能完成迁移或安全拒绝时不切换新契约
- 验收证据：版本一致性、数据库迁移、新旧样例、消费端联调和不兼容失败测试
- 关联需求：`DATA-PORT-001`、`DATA-QUALITY-001` 至 `DATA-QUALITY-003`、`INT-EXT-002`、`INT-PACKAGE-002`、`INT-FILE-002`

## 4. 依赖与环境配置

#### DEV-DEP-001：运行依赖最小、锁定且可追溯

- 状态：已接受
- 优先级：P0
- 来源：后端、前端、插件、测试和发布工具依赖的第三方软件会直接影响可重现性和供应链安全
- 质量要求：只引入当前需求必需的依赖，使用可重现的锁定版本并保留来源与许可证信息；引入或升级时检查已知高风险漏洞和实际用途
- 失败边界：来源不明、无法锁定、许可边界不清或存在未处置高风险漏洞的依赖不进入发布结果
- 验收证据：干净环境安装与测试、锁定文件差异、依赖用途审查及适用的漏洞扫描
- 关联需求：`SEC-SECRET-003`、`SEC-TRUST-002`

#### DEV-DEP-002：配置按环境注入并在启动时验证

- 状态：已接受
- 优先级：P0
- 来源：本地开发、测试和生产运行需要不同的数据库、来源白名单、日志级别和系统密钥
- 质量要求：环境差异通过明确配置注入，仓库只保留无真实秘密的配置模板；必需配置在服务或工具启动时校验并给出可操作的脱敏错误
- 失败边界：不用硬编码生产值、空密钥或临时随机密钥默认继续运行；配置无效时在产生业务副作用前停止
- 验收证据：开发、测试和生产配置模板检查，必需配置缺失、无效及秘密扫描测试
- 关联需求：`SEC-SECRET-001`、`SEC-SECRET-002`、`SEC-SECRET-003`

## 5. 编码与错误处理

#### DEV-CODE-001：实现只扩展已接受需求的必要边界

- 状态：已接受
- 优先级：P0
- 来源：v1 是重构主版本，现有实现只是事实和历史证据，不是必须保留的结构
- 质量要求：实现必须能回链已接受需求、设计或已确认风险；优先使用职责单一、可测试的最小方案，不预建未确认的通用化、兼容层、扩展点或隐式状态
- 失败边界：需求、设计和实现冲突时先停止实现并明确真源；不通过增加未证实复杂度掩盖未知需求
- 验收证据：变更与需求编号、设计和测试的追溯检查，以及无关变更审查
- 关联需求：`CONSTRAINT-06`

#### DEV-CODE-002：错误有明确类型、安全结果和根因证据

- 状态：已接受
- 优先级：P0
- 来源：认证、保存、发布、授权、安装、导入和运行时均存在可恢复与不可继续的失败
- 质量要求：预期失败使用稳定类型和可理解结果，未预期失败保留脱敏诊断关联信息；修复前先复现偏差并定位根因，重复、高代价或可复用的经验进入 `doc/lessons.md` 或后续分级经验目录
- 失败边界：不吞掉错误、不把部分成功写成全部成功、不在根因不明时连续叠加猜测性修复
- 验收证据：主要失败的错误契约、负向测试、日志关联、回归测试及适用的 lessons 记录
- 关联需求：`FR-AUTH-011`、`FR-PUBLISH-004`、`FR-GRANT-012`、`FR-LIB-013`、`FR-RUNTIME-014`、`DATA-QUALITY-003`

## 6. 测试与验收证据

#### DEV-TEST-001：每个实现步骤先定义可观察的完成条件

- 状态：已接受
- 优先级：P0
- 来源：需求已为正常、失败、恢复及安全边界建立可验收结果
- 质量要求：实现前先写明验收标准、输入、输出、状态变化、主要失败和至少一个边界条件；能自动化的使用自动化测试，只能在真实浏览器或外部环境确认的写出可重复手工步骤和预期结果
- 失败边界：没有可检查完成条件的实现不开始；“正常路径跑通一次”不表示失败、恢复或边界已通过
- 验收证据：开发计划中的测试方式、先失败的新测试或已记录基线、实现后测试结果及手工验收记录
- 关联需求：全部已接受 `FR-*`、`DATA-*`、`INT-*` 和 `SEC-*`

#### DEV-TEST-002：测试层次与真实风险相匹配

- 状态：已接受
- 优先级：P0
- 来源：KnownMap 同时包含纯逻辑、数据库事务、API、文件、Chrome 插件、B 站页面和真实发布环境
- 质量要求：单元测试验证核心规则，集成测试验证真实数据库、文件和模块协作，端到端或可重复手工测试验证教师发布到学生本机学习的真实边界；外部付费或不稳定依赖可替换，本地可控核心逻辑不被模拟掉
- 失败边界：不用全量模拟测试代替数据库事务和真实 Chrome/B 站边界；依赖外部状态的结论未经真实环境验证时明确标记未完成
- 验收证据：单元、集成、端到端与手工测试清单，核心业务闭环结果及真实浏览器证据
- 关联需求：`SCN-E2E-01`、`INT-EXT-001` 至 `INT-EXT-003`、`INT-BILI-001`、`INT-BILI-002`

#### DEV-TEST-003：变更和缺陷都有回归保护

- 状态：已接受
- 优先级：P0
- 来源：v1 重构需要保护已确认的业务行为，但不默认保留旧实现细节
- 质量要求：功能变更同步更新相关测试；缺陷修复先建立能重现偏差的失败测试或手工基线，修复后运行相关套件及受影响的全量回归
- 失败边界：只验证修改后结果、没有证明基线能暴露原偏差时，不声称回归保护已建立
- 验收证据：失败基线、修复提交、相关测试及受影响全量套件的前后结果
- 关联需求：`DATA-QUALITY-002`、`DATA-QUALITY-003`

第一阶段不设置没有项目基线的统一覆盖率数字。设计阶段应按模块风险明确测试范围；即使行覆盖率较高，
缺少主要失败、边界、权限、原子性或真实浏览器证据仍视为未完成。

## 7. 日志与诊断

#### DEV-LOG-001：关键业务动作具有安全的诊断链

- 状态：已接受
- 优先级：P0
- 来源：登录、保存、发布、授权、下载、安装、导入和恢复需要在不读取业务正文的前提下定位失败
- 质量要求：每个关键动作记录状态、类型、安全关联标识、成功或失败、必要耗时及脱敏错误摘要；同一请求或任务的记录可串联，日志级别由配置控制
- 失败边界：日志不包含密码、会话、授权码、系统密钥、完整课程正文或学生本机学习数据；日志不足以定位时不用记录原始敏感输入补救
- 验收证据：关键路径成功、失败和重试日志，关联标识串联检查，日志级别测试及敏感数据扫描
- 关联需求：`FR-ADMIN-003` 至 `FR-ADMIN-006`、`DATA-OPS-001`、`DATA-OPS-002`、`SEC-SECRET-001` 至 `SEC-SECRET-003`、`SEC-PRIV-002`

第一阶段不建立集中日志平台、全链路追踪、独立指标系统或凭感觉设置的告警阈值。真实服务规模出现后，
再根据实际日志量、错误率、处理责任和响应目标重新审核。

## 8. 文档同步与变更门禁

#### DEV-DOC-001：代码与当前权威文档同步变更

- 状态：已接受
- 优先级：P0
- 来源：v1 要求需求、设计、实现、测试和发布证据可追溯
- 质量要求：产品行为、数据、契约、架构、配置或运行流程改变时，在同一小步变更内更新对应权威文档、决策状态、计划、索引和验证入口；只有已验证结果进入 changelog
- 失败边界：文档与实现冲突时不默认代码正确；先确认是实现偏离、文档过期还是原决策已满足重开条件
- 验收证据：提交差异中的需求、决策、设计、数据、测试、索引、计划和 changelog 一致性检查
- 关联需求：`CONSTRAINT-06`、`DATA-QUALITY-003`

#### DEV-DOC-002：只有通过相关门禁的单一变更进入主线和发布

- 状态：已接受
- 优先级：P0
- 来源：小步变更需要可验证、可回溯且不混入无关修改
- 质量要求：每个提交或合并单元只包含一个明确目标及其必要文档和测试；进入主线或发布前通过相关自动化测试、必要手工验收、格式与静态检查、密钥及依赖扫描和文档同步检查
- 失败边界：任一当前适用的 P0 需求或验证门禁未通过时不合并、不发布；无法执行的检查必须明确原因、风险和补充验证，不写成已通过
- 验收证据：干净差异、提交边界、测试摘要、审查结论、安全扫描和手工验收记录
- 关联需求：全部已接受 `DEV-*` 及其关联需求

## 9. 第一阶段完成条件

本文件只在以下条件全部成立时完成：

1. 六类 `DEV-*` 均通过人工审核，并能回链已接受需求和安全边界；
2. 设计与开发计划为每个实现步骤明确代码范围、测试层次、日志证据、文档同步和提交时机；
3. 关键业务闭环有自动化测试与真实环境证据，两者覆盖范围和未验证项被准确记录；
4. 发布候选的契约、依赖、配置、日志、测试、文档和实际代码状态一致。

## 10. 当前暂缓事项

- 没有真实基线的统一覆盖率、测试时长和代码规模门槛；
- 全量 Chrome、操作系统、屏幕、B 站版本和网络组合的兼容实验室；
- 集中日志、独立指标、全链路追踪和复杂告警平台；
- 与当前业务无关的通用 SDK、微服务、扩展平台和多环境发布编排；
- 部署拓扑、备份恢复、监控告警、发布和回滚的具体运行要求，它们进入 `10-deployment-operations-requirements.md`。

暂缓项不影响当前必要的测试、错误处理、日志脱敏、依赖锁定、密钥扫描和文档同步门禁。

本文件通过后，下一篇为 `10-deployment-operations-requirements.md`。
