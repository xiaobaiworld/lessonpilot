## 1. 目标与边界

本文件定义如何证明 v1 真正交付了已接受需求。“代码已写”、“测试很多”、“页面已上线”或“演示跑通”都不能单独代替需求证据。

追踪单元是稳定编号。每个编号必须能向下追到设计、实现、测试、真实环境和发布记录，也必须能从任一新产物反向追回它所实现的需求。

本文件使用五类 `ACC-*`：

| 编号域 | 责任 |
| --- | --- |
| `ACC-COVER-*` | 所有已接受稳定编号进入需求级矩阵 |
| `ACC-LINK-*` | 需求与决策、设计、代码和证据双向链接 |
| `ACC-EVIDENCE-*` | 验收结论使用可定位、可重复的准确证据 |
| `ACC-CHANGE-*` | 上游变化后失效证据被重新评估 |
| `ACC-GATE-*` | P0 需求和运行门禁全部通过后才发布 |

## 3. 需求级矩阵字段

矩阵本体是机器可读文件 [`doc/traceability/v1-requirements.tsv`](../../traceability/v1-requirements.tsv)，
由 `node tools/build-traceability.mjs` 生成，每个稳定编号一行。本文件只保留字段定义、
状态取值和发布门禁。

矩阵列：稳定编号、定义文件、标题、需求状态、优先级、来源、关联需求、设计证据、实现证据、
自动化证据、真实环境证据、最终状态、最近检查。

前六列由需求文档解析，重新生成时覆盖。后七列由矩阵自己拥有，重新生成时保留已填内容，
由各实施阶段回填。`关联需求` 属于后者：需求条目不再保存该字段，上下游关系只在矩阵维护一次。

最终状态只能是：待设计、待实现、待验证、已验证、阻塞、不适用、已替代或已发布。“不适用”必须链接已接受需求或决策依据。

`node tools/build-traceability.mjs --check` 校验矩阵与需求文档一致；
`node tools/doc-check.mjs` 校验编号覆盖、无重复、无未定义编号；
`node tools/endpoint-check.mjs` 校验 HTTP 端点清单与后端实现对照。
三者都在 `npm test` 中运行。

## 4. 覆盖与链接

#### ACC-COVER-001：所有已接受稳定编号都进入矩阵且不重复

- 状态：已接受；优先级：P0
- 验收要求：每个当前有效编号恰好出现一次；已替代编号保留原行并链接替代项；需求状态变化时同步更新矩阵。
- 失败边界：遗漏、重复、未知编号或状态与需求真源冲突时检查失败。
- 证据：自动编号差集、重复检查、替代链及人工状态复核。
- 关联：`CONSTRAINT-06`、`DEV-DOC-001`

#### ACC-LINK-001：每项产物与稳定需求双向可追溯

- 状态：已接受；优先级：P0
- 验收要求：每条需求能向下找到负责的设计、实现和证据；每个新模块、契约、迁移、测试和发布步骤能反向说明它实现哪条当前需求。
- 失败边界：无需求产物视为无依据范围；找不到实现或证据的 P0 需求视为未完成。
- 证据：正向需求链接、反向产物链接及无需求产物清单。
- 关联：`DEV-CODE-001`、`DEV-DOC-001`、`MIG-SOURCE-001`

#### ACC-LINK-002：追踪状态只表示已有证据的阶段

- 状态：已接受；优先级：P0
- 验收要求：“已实现”链接 v1 代码或迁移产物；“已验证”对应当前代码与环境；“已发布”有正式发布记录和发布后验证。
- 失败边界：旧原型测试、历史截图、同名功能或单次演示不足以提升 v1 状态。
- 证据：状态变更记录、代码版本、证据链接、环境和检查时间。
- 关联：`MIG-SOURCE-001`、`OPS-RELEASE-001`

## 5. 证据要求

## 5A. 产品成功门槛

依据 `D-V1-005`，v1 发布候选必须同时满足以下闭环证据：至少一位真实老师使用真实课程完成建立、互动设计、保存和发布；至少一位真实学生成功领取、运行并完成互动；同一流程在另一门课程或另一位老师上重复成功；本机重启恢复、授权更新、失败恢复和回滚通过；全过程不需要开发者修改代码或直接改生产数据。

市场价值暂不设固定样本量、观察周期、完成率、再次使用率或支持成本数字，只记录真实交付意愿、学生实际互动、老师再次使用意愿和人工支持成本。取得真实数据后再重开数值门槛。

#### ACC-EVIDENCE-001：验收证据可定位、可重复且准确说明范围

- 状态：已接受；优先级：P0
- 验收要求：每项证据记录需求、入口、输入、预期、实际结果、代码版本、环境、时间及未覆盖边界；使用匿名或虚构数据并能重新执行或复核。
- 失败边界：只有“通过”文字、不含版本或环境、输出丢失、已过期或包含敏感原文的记录不作为发布证据。
- 证据：样例复核、重复执行、版本与环境检查及敏感数据扫描。
- 关联：`DEV-TEST-001`、`DEV-TEST-002`、`SEC-PRIV-002`

#### ACC-EVIDENCE-002：自动化和真实环境证据覆盖各自适合的边界

- 状态：已接受；优先级：P0
- 验收要求：业务规则、校验、权限、原子性、幂等和错误契约优先自动化；真实 Chrome、B 站、公网、备份恢复和升级顺序使用可重复环境证据。
- 失败边界：不用 mock 证明真实宿主或公网可用；不用单次人工点击代替可稳定自动化的核心规则。
- 证据：需求与证据类型对照、自动化套件、真实环境记录及未验证项清单。
- 关联：`DEV-TEST-002`、`OPS-RELEASE-002`、`MIG-CUTOVER-001`

## 6. 变更与证据失效

#### ACC-CHANGE-001：上游变化后重新评估受影响证据

- 状态：已接受；优先级：P0
- 验收要求：需求、决策、契约、数据、代码、依赖、宿主环境或迁移源变化时，标记受影响矩阵行并退回合适的待完成状态，直到重新评审与执行。
- 失败边界：不因代码名称、测试名称或页面外观未变就默认历史证据继续有效。
- 证据：变更影响分析、状态回退记录、重新执行证据及未重验项清单。
- 关联：`DEV-STRUCT-002`、`DEV-TEST-003`、`DEV-DOC-001`

当前影响记录：`D-V1-010` 允许课程内重复安排相同或相近内容，并允许多课节复用同一视频。旧课程包“重复 BVID 必须拒绝”的代码与测试只能
作为 v0.9.1 迁移证据，不能作为 v1 验收证据。`FR-COURSE-004`、`FR-COURSE-008`、`FR-RUNTIME-003`、
`DATA-CONTENT-001`、`DATA-CONTENT-002` 和 `INT-BILI-001` 的 v1 证据必须覆盖内容重复课节的保存与状态隔离、同视频多课节匹配、人工选择和会话锁定。

`D-V1-018` 新增的 `FR-PUBLISH-012`、`FR-PUBLISH-013`、`FR-GRANT-014`、`DATA-DELIVERY-007` 至
`DATA-DELIVERY-009` 当前只有需求和设计证据，不能标记为已实现或已验证。未来课程族升级、旧授权码默认查看新版本和
跨独立课程更新属于 `FR-GRANT-015` 的后续范围，本次不产生实现证据。

## 7. 发布门禁

公开销售页与飞书试用申请属于 v1 P0。发布候选必须包含公开入口真实可访问、最小字段提交、人工跟进、管理员确认后创建教师账号，以及未授权人员无法读取申请的验收证据；申请不得自动授予账号、工作空间或课程权限。

#### ACC-GATE-001：任一适用 P0 需求未完成时不发布 v1

- 状态：已接受；优先级：P0
- 验收要求：发布候选的所有适用 P0 矩阵行达到“已验证”；不适用有已接受依据；阻塞、待验证、证据过期或无法重复均阻止发布。
- 失败边界：不以进度、演示可用、旧版已上线或人工印象绕过 P0；例外必须先更改需求或建立已接受决策。
- 证据：P0 完整性检查、阻塞清单、证据有效性复核及发布决策记录。
- 关联：`DEV-DOC-002`、`OPS-RELEASE-001`、`OPS-RELEASE-002`

#### ACC-GATE-002：发布记录固定实际产物和最终验证结果

- 状态：已接受；优先级：P0
- 验收要求：正式发布记录精确代码版本、Web/API/插件/迁移产物、依赖、配置、环境、恢复点、发布前门禁、发布后探针、未解决风险和回退入口。
- 失败边界：发布中断、产物不一致、迁移对账失败或发布后核心探针失败时，记录真实失败状态而不标记已发布。
- 证据：发布记录、产物身份、迁移对账、公网探针、版本查询及回退验证。
- 关联：`DATA-OPS-002`、`OPS-RELEASE-001`、`OPS-RELEASE-002`、`OPS-INCIDENT-001`、`MIG-CUTOVER-001`
