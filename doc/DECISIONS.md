## D-015 教师平台先实现本地发布与插件授权下载切片

- 日期：2026-08-18
- 状态：已接受，待实现验证
- 问题：第一阶段销售页和原型 Demo 已完成，当前需要补齐教师发布和学生取得课程的真实能力，但暂时不需要完整学生平台。
- 已确认事实：后端采用 FastAPI 风格；本地采用 SQLite；教师账号手工预建；教师使用登录名和密码；当前一门课程只有一个课节；当前支持重点内容、选择题、填空题和问答题；学生只能通过 KnownMap 提供的解压版 Chrome 插件访问课程；当前要考虑未来公网部署，但本轮只做本地运行。
- 方案 A：一次实现 v0.2 全部教师、学生、授权和学习数据能力。
- 方案 B：先实现教师登录、课程/课节、四种节点、发布、授权码和插件课程下载。
- 决定：采用方案 B。授权码只绑定已发布课程并作为插件下载凭证，不创建学生身份、领取记录或学习数据。
- 放弃方案 A 的原因：超出当前开发测试闭环，增加学生身份、授权并集、数据上传、报表、管理员后台和公网运行环境等尚未需要的复杂度。
- 影响：新增 `backend/` FastAPI/SQLite 服务；教师界面从原型状态接入 API；插件增加授权码下载入口；当前不新增学生表和学习事件表。
- 假设：手工预建测试账号、解压版插件和一门一课节课程足以完成当前验证。
- 重开条件：测试必须证明学生身份或学习数据；教师需要多课节；授权码必须停用/过期/限额；学生不能接受插件入口；本地 SQLite 无法承载测试。
- 详细记录：`doc/decisions/2026-08-18-teacher-platform-local-slice.md`。

## D-010 GitHub Pages 采用发布期组装，公网只暴露页面与共享契约

- 日期：2026-08-15（2026-08-18 更新状态）
- 状态：已接受，Pages 发布已验证
- 问题：`A-DATA-01` 要求网页和插件复用同一份课程契约，并明确禁止两份相似校验器。但两者是不同分发单元：网页部署到 GitHub Pages，插件从本机 `src/` 以已解压方式加载。契约文件必须同时被两边取到，而契约放在 `src/shared/` 时，公网页面要引用 `../src/shared/`，这要求把仓库根目录整体发布。
- 已确认事实：仓库 `xiaobaiworld/lessonpilot` 是公开仓库（`private: false`），但公开仓库与"把全部文件放到可直接抓取的 Pages 站点"不是同一件事。`doc/` 当前包含竞品与定价研究、销售话术、多创作者商业与计费预案。
- 方案 A：Pages 以 `main` 分支根目录为源，页面引用 `../src/shared/`。
- 方案 B：契约移到仓库根 `shared/`，Pages 只发布 `teacher-web/` 与 `shared/`。
- 方案 C：契约源文件唯一存放 `src/shared/`，用 GitHub Actions 在发布期把 `teacher-web/` 与 `src/shared/` 组装成 artifact 发布。
- 决定：采用方案 C。Pages 源设为 GitHub Actions；workflow 以白名单方式显式列举要发布的文件。当前发布集为工作台诊断页及其两个页面脚本、销售页及其两个脚本，加 `shared/bridge-protocol.js` 与 `shared/course-contract.js`；`shared/workspace-origins.js` 只在插件侧使用，不上公网。销售页及其脚本是 1B 修订时按本决策的白名单方式追加的。
- 理由：同时满足"唯一契约源文件"和"不把商业资料与插件运行时代码发上公网"。用白名单而非排除法，是因为以后往 `doc/` 增加文件时，排除法会因为忘记加规则而静默泄漏，白名单不会。
- 放弃 A 的原因：`doc/` 下的定价研究、销售话术和商业预案进入公网可索引范围，且被抓取后不可逆；换取的只是省掉一个 workflow。
- 放弃 B 的原因：MV3 不允许扩展引用其根目录之外的文件，实际需把 `src/` 全部提到仓库根或做副本，改动面大于 C，且副本会破坏"唯一契约"这一需求本身。
- 代价与假设：页面对契约的引用路径本地为 `../src/shared/`、公网为 `./shared/`。该差异集中在 `workspace.html` 的一处脚本路径，并由测试锁定；假设组装产物 `teacher-web/shared/` 始终被 `.gitignore` 排除，不会变成提交进仓库的第二份副本。
- 已验证：Pages 于 2026-08-16 首次发布成功（run `31957352973`），发布清单只含白名单文件；2026-08-18 实测公网页面与两个契约文件返回 200，`/doc/` 与 `/src/` 返回 404。
- 重开条件：需要自定义域名；Pages 在目标老师网络不可用（并入 D-007 重开条件）；或页面与插件之外出现第三个契约消费方。
- 影响：新增 `.github/workflows/pages.yml`；`.gitignore` 增加 `teacher-web/shared/`；`doc/requirements/stage-1a.md` 的 A-DEPLOY-02 由本决策提供实现方式。

## D-011 课程契约按执行层分工，错误码不成为插件探测信号

- 日期：2026-08-15
- 状态：已接受
- 问题：实施 1A 前逐条核对 `doc/data-spec.md` 与 `doc/requirements/stage-1a.md` 时，发现五处规则无法在单一层执行，或按字面实现会与 1A 完成定义冲突。
- 事实与处置：
  1. **`captionId` 引用完整性**：data-spec §8 要求非空 `captionId` 必须引用现有字幕，但 `PluginCourseConfig` 按 A-DATA-02 不含 `captions`，插件侧没有字幕可比对，该规则在插件侧物理上无法执行。决定拆两级：共享契约只校验格式（非空、ASCII、≤80）；"必须引用现有字幕"归 `WorkspaceDraft` 层，由 1B 草稿校验器执行。规则不被放弃，只是明确归属层。
  2. **`INVALID_CHANNEL` 语义**：若 channel 不匹配时 content script 回错误响应，白名单页面上任意第三方脚本就能用错误码探测插件是否安装。决定 channel 不匹配时静默丢弃、不产生任何响应（该消息在语义上不是发给本桥的）；`INVALID_CHANNEL` 保留给 background 校验 content script 转发的信封，属内部一致性检查。channel 匹配但版本不支持仍返回 `UNSUPPORTED_VERSION`。
  3. **`updatedAt` 归属**：若 background 保存时重写 `updatedAt`，1A 完成定义第 4 条"保存后读取的课程与写入课程深度相等"永远失败。决定由页面产生并通过校验，background 原样存储、原样回显，只校验它是合法 UTC ISO 串。
  4. **normalize 与 validate 分工**：data-spec 要求节点有序，1A 计划要求乱序拒绝，A-DATA-01 要求不静默修复语义错误。决定 `normalizeCourse()` 负责排序并返回新对象，`validateCourse()` 对乱序直接拒绝不排序；写入侧先 normalize 再 validate，background 只 validate——插件不替网页修数据。
  5. **`enabled: false` 语义**：1A 只校验类型，不赋予过滤语义；"至少一个节点"按数组长度判断，不看 `enabled`。运行时行为属 1C。
- 放弃的做法：在插件侧放宽或删除 `captionId` 规则（会让规则消失而非归位）；让 channel 不匹配返回错误码（会形成探测信号）；让 background 生成 `updatedAt`（会与完成定义冲突）。
- 假设：1B 实现 `WorkspaceDraft` 校验器时会承接 `captionId` 引用完整性；若 1B 未承接，该规则会在无人执行的状态下丢失。
- 重开条件：`PluginCourseConfig` 未来需要携带字幕子集；或 1C 定义 `enabled: false` 的运行时行为时发现需要在契约层过滤。
- 影响：`doc/data-spec.md` 新增第 13 节记录以上分工；`src/shared/course-contract.js` 与 `src/background/` 按此实现。

- 安全文案边界：只陈述当前可验证事实：公开代码、有限页面范围、本地存储、未匹配课程不启动互动；不声称第三方安全审计或绝对安全。
- 表单字段：称呼、联系方式、视频状态/链接、最想解决的教学问题、字幕情况；不收集无关长问卷。
- 假设：飞书表单公开 URL 由开发者提供并可接收提交；若没有可用 URL，页面只保留私信 CTA，不伪造表单入口。
- 重开条件：真实老师更愿意填写表单而不是私信，或微信/B 站私信无法承接第一轮联系。
- 相关需求：`doc/requirements/stage-1b.md` 的 WEB-05、WEB-06。

## D-013 个性化教学先验证需求，不作为当前销售承诺

- 日期：2026-08-16
- 状态：待验证的产品方向
- 设想：未来根据不同学生的回答调整后续问题、难度、讲解或反馈，使同一课程提供不同的学习路径。
- 当前事实：当前试用只在老师设定的固定时间点展示固定节点；选择题和填空题使用确定性反馈，问答题只展示老师预设反馈，不根据学生差异动态生成内容。
- 决定：个性化教学不进入首屏、“加入互动”价值区或当前功能清单；不得写成已完成或当前试用包含的能力。
- 验证方式：在飞书表单和老师访谈中询问这项能力的重要程度，以及老师希望系统根据哪些差异调整教学。
- 表单问题：`如果课程能根据学生的不同回答，调整后续问题和反馈，这项能力对您有多重要？`
- 选项：`没有它也可以试用`、`有帮助，但不是必要条件`、`非常重要`、`没有这项能力，我不会使用`。
- 补充问题：`您最希望系统根据学生的哪些差异调整教学？`，用于区分难度、题目、反馈、补充讲解和学习路径。
- 对外表述：只有在需要介绍未来方向时才能写“正在验证根据学生回答调整后续问题和反馈的个性化教学能力；当前试用暂不包含此功能”。
- 重开条件：真实老师反馈形成明确、重复的需求，并且当前固定节点闭环已经完成验证。

## D-014 KnownMap 作为长期品牌，采用地图窗口圆形 Logo

- 日期：2026-08-18
- 状态：已接受，已完成资源生成、项目替换和视觉验证
- 问题：当前 `LessonPilot` 名称绑定课程与视频，不能直接承载长期知识平台方向；现有 LP 方形图标也没有表达内容连接、知识路径和继续探索。
- 已确认事实：用户已购买并指定 `knownmap.com`；现有项目视觉体系使用深墨绿、暖纸白、低饱和节点色；视觉对比中用户最终确认 A 方向。
- 方案：采用深墨绿圆形底的“地图窗口”图标。浅灰绿外轮廓表达知识空间；一条纸白内部路径表达理解路径；金色与陶土色节点表达关键停靠点；两条竖向折页线保留但使用同一种低强度纸白色，收在地图边界内部。
- 放弃方案：无竖线版本（小尺寸更简洁但地图折页含义较弱）；两条异色竖线（层级明显但增加颜色噪声）；虚线竖线（大尺寸有设计感但小尺寸容易碎）；继续使用旧 LP 图标（与新品牌不一致）。
- 决定：品牌文字使用 `KnownMap`，域名文字使用 `knownmap.com`；正式资源统一基于同一精修几何导出 16px、24px、48px、128px PNG，并同步网页 favicon、manifest 名称、页面用户可见品牌和当前入口文档。
- 非目标：不改 GitHub Pages origin、路径白名单、协议 channel、存储键、内部 `lessonpilot` 命名空间和历史归档品牌。
- 假设：统一品牌文字不会改变第一阶段用户流程；现有深墨绿和暖纸白体系足以承载 KnownMap，不需新增渐变或高饱和主色。
- 重开条件：实际 16px/24px 资源无法保持路径和节点可识别；真实用户测试显示品牌名称与页面产品定位发生混淆；或域名、商标、组织名核验出现冲突。
- 影响：新增品牌设计规范；后续修改 `src/assets/`、`src/manifest.json`、teacher-web 用户可见品牌文字、当前文档入口与相关测试；内部协议和历史资料保持兼容。
- 设计文档：`docs/superpowers/specs/2026-08-18-knownmap-brand-update-design.md`
- 资源说明：`docs/knownmap-logo-resources.md`；当前提供圆形深绿底、方形深绿底和透明背景三种共用几何的 SVG 变体。透明版边缘与主路径使用品牌深绿色 `#1D5C43`，不使用纯黑。
- 验证：`node --test tests/*.test.js` 通过（204 pass / 0 fail）；已检查 16/24/48/128 PNG 尺寸，并在桌面与 375px 移动端检查销售页、工作台 Logo 显示。
