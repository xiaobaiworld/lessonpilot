## D-020 Web 生产发布绑定 GitHub 提交并保留不可变历史

- 日期：2026-08-18
- 状态：已验证
- 问题：`knownmap.com` 已经发布销售首页，但初次部署目录只包含时间戳，不记录 GitHub commit、文件清单或可查询的回滚历史。系统重装、后续改版或线上故障时，无法快速证明线上对应哪个源码版本。
- 已确认事实：生产服务器通过 SSH 别名 `aliyun` 连接；Nginx 使用 `/var/www/knownmap/current`；当前只允许销售页白名单进入公网；教师 API 和教师编辑器仍属于本地阶段。
- 方案 A：继续手工复制文件并在对话中记录版本。
- 方案 B：每次覆盖固定目录，只把当前 commit 写入一个文本文件。
- 方案 C：从已经推送到 GitHub 的精确提交构建白名单发布包，为每次发布保存元数据和文件哈希，通过符号链接原子切换，并创建 GitHub 生产标签。
- 决定：采用方案 C。发布目录不可变；`release.json` 保存完整 SHA、GitHub 标签、发布时间、前一版本和公开文件哈希；服务器使用 JSONL 追加历史；仓库使用一份 JSON 文件记录一次成功发布。
- 发布门禁：目标提交必须存在于 `origin` 远端分支历史；发布包必须来自 `git archive`；销售页测试通过后才上传；首页哈希、健康检查和私有路径 404 均通过后才确认成功。
- 失败恢复：切换后验证失败或 GitHub 标签推送失败时，自动原子切回前一发布目录并记录失败事件。
- 回滚：只允许切换到仍保留在服务器、元数据存在且 `SHA256SUMS` 校验通过的发布；回滚后再次执行相同线上验证。
- 安全边界：不发布教师编辑器、后端、测试、文档、插件源码、`.git` 或环境文件；发布记录不保存密码、SSH 私钥、Cookie、授权码或环境变量；不自动删除旧发布。
- 放弃方案 A 的原因：聊天记录不是可执行、可校验的生产事实源。
- 放弃方案 B 的原因：覆盖目录会丢失回滚目标，单一文本记录也不能证明文件内容。
- 重开条件：教师 API 或教师编辑器进入生产；迁移到容器、对象存储、CDN 或托管发布平台；需要多人审批、自动保留策略或数据库迁移编排。
- 验证：`7cab05f6ff46394b86cf4bdcb8b380eb41cd3b78` 已迁移为可回滚发布；当前生产版本是 `f8e09e172bd3be980b664c81f9e1c7535819ae77`。两个发布目录的 9 个公开文件均通过 SHA-256 校验；首页线上哈希与 GitHub 源文件一致；健康检查通过；`/doc/`、`/src/`、`/tests/`、`/teacher-web/editor.html`、`/.git/config` 和 `/.env` 均返回 404。
- 详细设计：`doc/web-production-release-design.md`
- 实施计划：`doc/plans/web-production-release-traceability.md`

## D-017 教师应用使用“KnownMap 课程设计平台”定位并移除原型口吻

- 日期：2026-08-18
- 状态：已验证；产品类别称呼已由 D-019 替代
- 问题：教师端已经接入真实登录、课程、草稿、发布和授权码能力，但页面仍显示“功能原型”“开发账号”“本地 API”“W0 当前范围”等内部开发语言，并在登录页源码中预填测试密码。用户看到的是演示说明，不像可以持续使用的课程设计工具。
- 已确认事实：`KnownMap` 已由 D-014 确认为长期品牌；当前教师端的核心任务是设计和发布课程；测试教师使用预建账号登录；密码由本地 seed 环境变量提供，不应成为页面源码的一部分；当前仍只有一个课程和一个课节。
- 方案 A：把品牌整体改名为“课程设计平台”。
- 方案 B：保留 `KnownMap Studio`，只零散替换“原型”和“测试”文案。
- 方案 C：保留 KnownMap 品牌，把教师应用统一命名为“KnownMap 课程设计平台”，同时重整登录页、课程首页、编辑页层级和操作状态。
- 决定：采用方案 C。`KnownMap` 是品牌，“课程设计平台”是产品类别；教师可见界面只呈现账号、课程、课节、字幕、节点、草稿、发布和授权等真实任务。
- 登录规则：账号名可以为本地测试便利预填；密码不得在 HTML 或 JavaScript 中预填、记录或持久化；提供可访问的显示/隐藏密码控制；提交期间禁用重复登录。
- 界面语言规则：正常页面不显示“原型”“W0”“开发测试账号”“本地 API”等实施说明；连接异常可以显示面向用户的服务状态，具体诊断继续留在浏览器控制台和后端日志。
- 页面结构：登录页只完成身份验证；课程首页改为“我的课程”操作面，集中课程信息、视频链接和字幕；编辑页以课程名、课节、节点、保存、发布和授权为主，不使用营销式大标题或虚构播放器。
- 放弃方案 A 的原因：会丢失刚确认并完成资源化的 KnownMap 品牌。
- 放弃方案 B 的原因：只改几个词不能解决页面层级、假功能和内部说明侵入用户界面的问题。
- 假设：当前单课程、单课节范围不需要新增课程列表路由或后端接口；本轮可以只调整现有静态教师应用层。
- 重开条件：支持多课程或多课节；教师自主注册；需要面向公网展示环境或租户状态；品牌核验要求改变 KnownMap 名称。
- 影响：修改教师端 HTML、CSS、页面编排和前端契约测试；不修改 API、数据库、插件协议和课程节点 schema。
- 验证：登录密码不再出现在页面源码，登录成功和退出后都会清空；1440、900、375 三档浏览器无页面级横向溢出或脚本错误；键盘可以选择节点、调整时间并放置；字幕重绑进入最终草稿 payload；发布期间保存和编辑区域保持锁定；退出后课程、字幕、发布版本和授权码状态全部清空。
- 自动化证据：Node 234 pass，后端 37 pass，Bandit 无发现，`pip-audit` 无已知漏洞，JavaScript 语法和 `git diff --check` 通过。
- 详细设计：`doc/teacher-platform-experience-polish-design.md`
- 实施计划：`doc/plans/teacher-platform-experience-polish.md`

## D-018 学生插件采用单课程领取、字幕导航和本地学习状态

- 日期：2026-08-18
- 状态：已接受，部分验证。授权码公开下载、插件领取、单课程本地状态、匹配视频运行和工具栏首页已实现；完整真实 Chrome 边界验收待收口
- 问题：当前教师平台已经能发布课程并通过授权码返回插件配置，但学生插件还缺少完整的领取后行为、字幕句控制、课程打开入口和本地学习闭环。
- 已确认事实：老师负责设计四种线性互动；学生还需要上一句、下一句、一次复听、三次复听和持续循环；插件以陪伴式小助手为入口，授权和学习概览放在书包；测试阶段只需一门课程。
- 方案：多课程书包；一次性或设备绑定授权；单课程加可重复下载授权码。
- 决定：测试版只保存一门当前课程；授权码可重复使用并取得最新已发布课程包；课程包包含 B 站标识、结构化字幕句和四种节点；学生学习状态独立保存在本机。
- 领取后行为：插件校验并保存课程包，显示“打开课程视频”；插件根据 `platform + bvid + cid` 生成标准 B 站地址，学生点击后打开，页面再次核对 BVID 后启动课程。
- 学习状态：记录有效学习次数、节点状态、复听次数和确定性待复习清单；当前不上传后端。
- 放弃多课程的原因：会提前引入课程列表、授权并集和状态隔离，不能提高一门真实课程的验证效率。
- 放弃一次性或设备绑定授权的原因：会提前引入领取记录、设备身份、解绑和失败恢复。
- 安全边界：授权码原文不长期落库或进入日志；后端不返回任意跳转 URL；课程包和所有外部输入都先校验，失败时不覆盖原课程。
- 重开条件：真实测试必须同时保存多门课程；授权分享造成问题；需要停用、过期、人数或设备限制；学习数据需要跨设备或回传教师。
- 详细设计：`doc/student-plugin-course-delivery-design.md`。
- 详细记录：`doc/decisions/2026-08-18-student-plugin-single-course-delivery.md`。

## D-016 教师编辑器采用组件注册和可视化时间轴

- 日期：2026-08-18
- 状态：已验证
- 问题：节点 7 已接入真实 API，但当前教师编辑器以纵向字幕列表和右侧表单为主，不能表达老师在完整课节时间线上组合教学节点的核心工作方式。
- 已确认事实：`teacher-web/forsales.html` 已展示节点组件栏、横向时间轴、节点 marker、摘要和字幕上下文；该页面的节点仍是静态示例，组件按钮没有真实添加能力；用户明确要求点击添加和拖放添加两种方式都支持，并要求先写开发文档再改代码。
- 方案 A：保留当前字幕列表，只增加拖放样式。
- 方案 B：直接复制销售页的静态时间线和弹窗。
- 方案 C：以销售页为视觉参照，建立组件注册表和真实时间轴；点击后点击时间轴、拖放到时间轴共用同一创建动作；节点使用现有后端 schema 保存。
- 决定：采用方案 C。正式编辑器以节点为一级可视化对象，字幕只提供定位和上下文；四种节点通过注册机制组织；支持节点选择、弹窗编辑、拖动改时和删除。
- 选择理由：方案 C 同时满足可视化组合、真实草稿持久化和后续扩展节点类型，且不需要修改当前 FastAPI 草稿、发布和授权码接口。
- 放弃方案 A 的原因：主要编辑模型仍是字幕表单，不能解决用户指出的产品偏差。
- 放弃方案 B 的原因：静态节点和固定百分比无法服务真实课程，也会形成销售示例与正式数据两套事实源。
- 日志边界：已提交的保存、发布和授权动作继续进入后端 `OperationLog`；未提交的组件选择和拖动只输出分级、脱敏的前端诊断日志，不新增后端编辑事件 API。
- 假设：当前字幕最后结束时间可作为本地课节时长；原生 Drag and Drop、Pointer Events 和现有静态技术栈足以完成第一版。
- 重开条件：需要和真实播放器播放头实时同步；需要移动端触摸拖放作为主要入口；需要撤销/重做、多课节或多人协作；前端临时操作必须进入持久审计。
- 影响：已新增节点组件注册、时间轴模型、可视化控制器和前端日志模块；节点 7 已完成，下一步继续节点 8。
- 详细设计：`doc/teacher-visual-node-editor-design.md`。
- 实施计划：`doc/plans/teacher-visual-node-editor.md`。

## D-010 GitHub Pages 采用发布期组装，公网只暴露页面与共享契约

- 方案 B：契约移到仓库根 `shared/`，Pages 只发布 `teacher-web/` 与 `shared/`。
- 方案 C：契约源文件唯一存放 `src/shared/`，用 GitHub Actions 在发布期把 `teacher-web/` 与 `src/shared/` 组装成 artifact 发布。

- 代价与假设：页面对契约的引用路径本地为 `../src/shared/`、公网为 `./shared/`。该差异集中在 `workspace.html` 的一处脚本路径，并由测试锁定；假设组装产物 `teacher-web/shared/` 始终被 `.gitignore` 排除，不会变成提交进仓库的第二份副本。

- 影响：新增 `.github/workflows/pages.yml`；`.gitignore` 增加 `teacher-web/shared/`；`doc/requirements/stage-1a.md` 的 A-DEPLOY-02 由本决策提供实现方式。

## D-011 课程契约按执行层分工，错误码不成为插件探测信号

- 日期：2026-08-15
- 状态：已接受
- 问题：实施 1A 前逐条核对 `doc/data-spec.md` 与 `doc/requirements/stage-1a.md` 时，发现五处规则无法在单一层执行，或按字面实现会与 1A 完成定义冲突。
- 事实与处置：
  1. **`captionId` 引用完整性**：data-spec §8 要求非空 `captionId` 必须引用现有字幕，但 `PluginCourseConfig` 按 A-DATA-02 不含 `captions`，插件侧没有字幕可比对，该规则在插件侧物理上无法执行。决定拆两级：共享契约只校验格式（非空、ASCII、≤80）；"必须引用现有字幕"归 `WorkspaceDraft` 层，由 1B 草稿校验器执行。规则不被放弃，只是明确归属层。
  2. **`INVALID_CHANNEL` 语义**：若 channel 不匹配时 content script 回错误响应，白名单页面上任意第三方脚本就能用错误码探测插件是否安装。决定 channel 不匹配时静默丢弃、不产生任何响应（该消息在语义上不是发给本桥的）；`INVALID_CHANNEL` 保留给 background 校验 content script 转发的信封，属内部一致性检查。channel 匹配但版本不支持仍返回 `UNSUPPORTED_VERSION`。
  3. **`updatedAt` 归属**：若 background 保存时重写 `updatedAt`，1A 完成定义第 4 条"保存后读取的课程与写入课程深度相等"永远失败。决定由页面产生并通过校验，background 原样存储、原样回显，只校验它是合法 UTC ISO 串。
  4. **normalize 与 validate 分工**：data-spec 要求节点有序，1A 计划要求乱序拒绝，A-DATA-01 要求不静默修复语义错误。决定 `normalizeCourse()` 负责排序并返回新对象，`validateCourse()` 对乱序直接拒绝不排序；写入侧先 normalize 再 validate，background 只 validate——插件不替网页修数据。
  5. **`enabled: false` 语义**：1A 只校验类型，不赋予过滤语义；"至少一个节点"按数组长度判断，不看 `enabled`。运行时行为属 1C。
- 放弃的做法：在插件侧放宽或删除 `captionId` 规则（会让规则消失而非归位）；让 channel 不匹配返回错误码（会形成探测信号）；让 background 生成 `updatedAt`（会与完成定义冲突）。
- 假设：1B 实现 `WorkspaceDraft` 校验器时会承接 `captionId` 引用完整性；若 1B 未承接，该规则会在无人执行的状态下丢失。
- 重开条件：`PluginCourseConfig` 未来需要携带字幕子集；或 1C 定义 `enabled: false` 的运行时行为时发现需要在契约层过滤。
- 影响：`doc/data-spec.md` 新增第 13 节记录以上分工；`src/shared/course-contract.js` 与 `src/background/` 按此实现。
