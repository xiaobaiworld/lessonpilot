## 0. 文档定位

本文件回答一个 P2 产品化阶段的问题：

> 一个学习者 A 会观看多个创作者 b1、b2、b3 的视频。这些创作者各自定制的互动内容，如何准确、安全、可实时更新地送达 A？这套东西如何定义功能、如何收费、如何部署？

本文件**不修改**整理前 `doc/archive/2026-08-15-pre-stage-one/requirements.md` 的 P0 / D0 / D1 历史范围。当前第一阶段范围以 `doc/requirements.md` 为准。

平台扩展已拍板：D0/D1 只做 B 站；YouTube 为 D1 之后的第二个 `PlayerAdapter`；多语言与多地区完全延后。本文件其余待确认项仍须在对应阶段开工前拍板。

## 1. 角色与实体模型

### 1.1 三个角色

| 角色 | 身份 | 付费 | 在系统里的行为 |
|---|---|---|---|
| A：学习者 | 匿名或课程码绑定 | 课程访问通常已向老师付费；可选购买通用 AI 额度 | 安装插件，观看视频，作答，查看学习总结 |
| B：创作者 | 租户（tenant），有账号 | 是，B 是付费主体 | 编辑课程包，发布，查看学习证据 |
| 平台 | 服务方 | 收费方 | 存储与分发课程包，代理 AI 调用，鉴权与计费 |

关键点：**课程能力与 AI 能力有两条资金流。** B 为课程托管、分发和报告支付订阅；A 可为跨老师通用的 AI 额度付费，B 也可选购仅用于自己课程的定向额度。访问授权按老师隔离，AI 额度按学生记账，不能再假设所有配额和计费都挂在 B 身上。

### 1.2 核心实体

同一个视频可以存在多份不同的讲解。因此「视频的归属」和「讲解的作者」必须拆成两层，不能合并成一个 `creatorId`：

```text
Video（视频）
  └── VideoRef = { platform, videoId, partId? }
  └── ownerId        授权方，视频这一侧的主体

Lesson Pack（课程包 / 讲解包）
  └── packId
  └── videoRef       指向某个视频
  └── ownerId        授权方
  └── authorId       讲解作者
  └── version        已发布版本号
  └── status         draft / published / archived
  └── nodes[]        互动节点，结构沿用 doc/design.md 第 4 节
```

`ownerId == authorId` 表示视频方自己做讲解；两者不等表示视频方把讲解交给了别人。

**这两种情况共用同一套模型，不需要两条代码路径。** 当前 Demo（老师用自己的视频做自己的讲解）就是 `ownerId == authorId` 的退化形态。将来开放「授权给别人做」只是允许两个字段不相等，并补一条授权记录，不是重写。

课程包是分发、版本、权限和计费的**最小单元**。

### 1.3 关系

- 一个授权方可以对同一个视频授权出多份讲解包；
- 一个讲解作者可以有多个讲解包，分布在不同视频上；
- 一个 A 的浏览器里会缓存来自多个作者的多个讲解包。

**一个视频可以对应多份生效的讲解包。** 这一点看起来会造成「学生端不知道该用哪份」，但实际上被入口设计化解了：学生是通过某个作者的课程码加入的，他加入了谁就用谁的版本。真正的冲突只发生在同一个学生同时购买了两位作者的课、且两人讲了同一个视频——这是边缘情况，第一版不提供版本选择界面，等它真实发生后再处理。

### 1.4 课程包只提供数据，不提供行为

**所有创作者共用同一套组件实现。课程包只声明「用哪个组件、属性填什么」，不携带任何代码、标记或样式字符串。**

这条原则已经体现在 `doc/design.md` 2.5 节（一个稳定的题卡容器 + 三个渲染器），此处将其上升为通则并说明理由。

#### 三项收益

**效率。** 组件代码属于插件本身，只加载一次，不随课程包下载。课程包退化为纯数据，体积极小，传输、缓存与本地占用都很低。组件类型固定，因此只需针对这几种做性能优化，不存在某个创作者写出低效代码影响全体的可能。

具体做法之一：题卡容器复用同一批 DOM 节点，切换节点时只更新内容不重建。这与历史 `doc/archive/2026-08-15-pre-stage-one/requirements.md` 11.4 节「三种题型使用稳定尺寸，切换状态时不造成明显布局跳动」是同一件事的两面。

**安全。** 该原则成立后，7.2 节「课程包必须当作不可信输入」的问题从「是否需要沙箱」降级为「校验若干字段的类型与范围」。创作者不具备表达行为的能力，也就不存在注入入口。

**可维护性。** 一处改进对全体创作者生效。反面是一处缺陷同时影响全体，因此这几个组件的测试密度必须高于其他部分。

#### 红线：组件类型是封闭集合，扩展权只在平台

这条原则的主要威胁不是技术，而是商业压力。典型情形是某个愿意多付费的创作者要求特殊样式或特殊题型，而最省事的实现方式就是在课程包里开一个允许自定义 HTML、CSS 或脚本的字段。

**一旦开放此类字段，上述三项收益同时作废**：安全上立即需要沙箱，效率上课程包开始膨胀，维护上每个客户变成一个特例。

因此：

- 组件类型是封闭枚举，只有平台可以新增；
- 创作者可以提需求，由平台评估后新增所有人可用的组件类型；
- **不提供任何形式的自定义代码入口，包括「只是少量 CSS」**；
- 可配置属性必须是枚举值或有范围约束的数值，不得是自由字符串。现有的字幕遮挡条样式配置需按此标准收紧。

#### 代价：插件版本不同步

「组件在插件里、数据在服务端」这一架构必然带来版本错配。学生的插件版本参差不齐：Chrome 自动更新有延迟，定向分发的未打包安装则完全不会自动更新。因此必然出现**老版本插件遇到使用了新组件的课程包**。

必须定义的降级行为：

1. 每个节点自带 `type`。插件遇到无法识别的 `type` 时**跳过该节点并继续播放**，不得崩溃或白屏。
2. 会话中明确记录「该节点因插件版本过低未显示」。**不得记为已完成，也不得记为学生跳过**——两者都会污染老师看到的学习证据。此项与历史需求 S07「跳过节点必须在总结中明确标记，不得伪装成已完成」同源，只是原因从学生主动跳过变为客户端能力不足。
3. 创作者后台应提示「本课程使用了较新组件，部分学生的插件版本可能过低」，否则老师会将其判定为产品故障。

### 1.5 组件族清单与收敛判断

1.4 节要求组件类型是封闭集合。那么这个集合应该有多大？

**结论：候选能力虽多，但收敛后只有四到五个组件族，其余全部是属性差异。** 判断一项新需求时，第一反应必须是「能否用现有组件族的属性表达」，只有确实不能，才考虑新增族。

#### 四个已存在或近在眼前的组件族

| 组件族 | 当前状态 | 同族成员（属性差异，不是新组件） |
|---|---|---|
| 定时覆盖层 | 已实现（S09 字幕遮挡） | 遮挡字幕、遮挡画面局部、遮挡屏幕上的答案或板书 |
| 定时播放行为 | 已有播放控制 spike；S03 可复用状态机待实现 | 区间循环复读、区间禁止跳过、区间变速、区间自动跳过 |
| 互动题卡 | S04/S05/S06 已定义，渲染器待实现 | 判断题（选择题的两选项特例）、听写题（填空题的长文本特例）、排序题、匹配题 |
| 定时文本标注 | 未实现 | 补充说明条、生词浮层、老师注释 |

#### 收敛的三个例子

**「遮挡画面局部」不是新组件。** 现有实现的版式参数已经支持定位到视频内任意矩形区域，只是当前配置恰好用成了底部整条。这项能力现在就已经具备，不需要任何新代码。

**「判断题」不是新组件。** 它是选项数量为二的选择题。

**「听写题」大概不是新组件。** 它是允许多行输入的填空题，可能只需要给填空渲染器加一个属性。

#### 需要单独归类的一项

**录音跟读与发音评价**属于另一个量级：它需要麦克风权限、涉及音频上传、依赖发音评测服务，成本结构和隐私影响都与现有组件完全不同。当前仍在 `doc/requirements.md` 第 6 节列为非目标，不应与上述组件族混为一谈。

#### 一处命名问题

现有实现命名为 subtitle blocker，但其实际能力是「任意矩形定时覆盖层」。命名比能力窄会限制后续设计者的想象，也会导致有人为「遮挡画面局部」重新实现一个组件。

建议在后续重构时更名为 timed overlay。**这是命名调整，不是当前需要执行的改动**，记录于此以免重复实现。

#### 当前阶段的结论

**不新增任何组件族。** 先确认已有的三个（覆盖层、暂停行为、三种题卡）在真实课程改造中是否够用。老师提出的需求应优先尝试用现有族的属性满足；确实无法表达时，由平台评估后新增所有人可用的族，而不是给该老师开自定义入口（见 1.4 节红线）。

**本节只覆盖「老师配置的内容组件」。** 学生端还存在另一个性质不同的类别——学生个人学习工具（生词收藏、错题重练、复习队列等），它由平台统一提供、跨课程通用、不由老师配置。两个类别的完整对照与调研计划见 `doc/student-runtime.md`。

## 2. 归属识别：打开一个视频，怎么知道它属于谁

这是「不串台」的核心问题。有两条线索：

**线索一：页面上的创作者标识。** B 站视频页面上有 UP 主信息。理论上可以从页面读取 UP 主 mid，与创作者注册时绑定的 mid 比对。

**线索二：服务端索引。** 服务端维护 `videoId -> [{ ownerId, authorId, packId, version }]` 的映射表，插件结合当前学生已加入的作者确定可用课程包。

**决策：以服务端索引为唯一权威来源，页面标识只做辅助校验。**

理由：页面数据在客户端，任何人都能伪造。如果允许插件凭页面上的 UP 主信息自行决定加载哪份内容，就等于把归属判定权交给了不可信环境。服务端索引则由「授权方证明自己拥有这个视频」这一步来保证正确性。

页面标识的价值在于**兜底告警**：如果服务端说这个视频的授权方是 b1，但页面显示 UP 主是别人，说明索引出错或视频被搬运，此时应当拒绝加载并上报，而不是硬着头皮渲染。

注意这里判定的是**授权方**，不是讲解作者。讲解作者不需要与页面上的 UP 主一致，他的合法性来自授权记录，不来自页面。

**待确认：授权方如何证明自己拥有某个视频。** 可选做法包括在视频简介里放一段校验码、通过平台开放授权、或人工审核。第一批客户量小，人工审核成本最低，但必须在自助注册开放前解决。这一项没有确定答案之前，不能开放自助绑定。

**待验证：B 站视频页面上 UP 主 mid 的稳定获取方式。** 我尚未在代码中验证过该字段的位置和稳定性，不能凭印象写进实现。

## 3. 分发架构选型

### 3.1 三个候选方案

**方案 A：纯本地打包（现状）**

课程内容随插件一起发布。多创作者场景下直接排除：每次任何一个创作者改一个字，都要重新发版并等待所有学生更新。

**方案 B：服务端拉取 + 本地缓存（推荐）**

插件在打开视频时向服务端请求该视频对应的课程包，带上本地缓存的版本号做条件请求；服务端返回新版本或「无变化」。本地缓存保证离线和弱网可用。

**方案 C：长连接推送（WebSocket / SSE）**

服务端在创作者发布时主动推送给在线的学生端。

### 3.2 选择方案 B，理由

1. **时效性需求不匹配。** 课程内容不是行情数据。学生真正需要的是「我打开这个视频的这一刻，拿到的是最新已发布版本」，而不是「视频播到一半，题目突然变了」。后者反而是有害的——学生正在作答时内容被替换，会话数据会自相矛盾。
2. **MV3 的硬约束。** Chrome Manifest V3 的 background 是 Service Worker，空闲后会被浏览器回收，无法稳定维持长连接。当前 `src/manifest.json` 已经是 MV3。要在 MV3 上做可靠推送，需要引入额外机制，复杂度和收益不成比例。
3. **成本。** 长连接意味着按在线学生数计算的常驻连接开销，而付费方是创作者。学生规模增长直接推高成本，但不直接增加收入。

**结论：不做实时推送。「实时」定义为「学生每次进入视频时取到最新已发布版本」。** 这个定义必须写进需求，避免和创作者沟通时产生「秒级同步」的预期错配。

## 4. 更新机制的具体设计

### 4.1 草稿与发布分离

创作者的编辑动作不能直接影响学生。必须区分两个状态：

- **草稿（draft）**：只有创作者本人可见，用于编辑和预览。老师预览走本地草稿，不等服务端往返；这里引用的是归档需求 T03 的历史设想。
- **已发布（published）**：学生端唯一可见的版本，带递增版本号。

这是现有 T02「校验失败不得覆盖上一份有效配置」原则在网络场景下的延伸：**没有通过校验和发布动作的内容，绝不进入学生端。**

### 4.2 学生端取数流程

A 在 B 站看的绝大多数视频都没有课程包。**不能对每个视频都去问服务端**，原因有两个：服务端会因此收到用户完整的观看历史（与需求 11.3 的最小数据原则冲突），且绝大部分请求是无效的 404。

因此按「从便宜到贵」分三层过滤：

```text
A 打开或跳转到某个视频
  -> 提取平台 + 视频 ID

  第一层：查本地视频索引（零网络）
       不在索引中 -> 直接结束，不挂载，不发任何请求   <- 绝大多数视频止步于此
       在索引中   -> 继续

  第一层附加：查该视频对应作者的授权状态（零网络）
       授权已过期 -> 明确提示已过期并指向续期，不静默
       授权有效   -> 继续

  第二层：查本地缓存新鲜度（零网络）
       缓存在新鲜期内 -> 直接使用
       过期或缺失     -> 继续

  第三层：向服务端条件请求（带 version / ETag）
       304 无变化   -> 用本地缓存，刷新缓存时间
       200 新版本   -> 校验结构 -> 写入本地缓存 -> 使用
       404/410 停止分发 -> 不再获取新包；已有缓存按 7.4 节的撤销规则处理
       网络失败     -> 回退到本地缓存；无缓存则不挂载

  -> 创建学习会话，锁定当次会话使用的版本号
```

**本地视频索引**是一份「A 已加入的作者名下，哪些视频有讲解包」的 ID 清单，只含标识不含内容。B 站 BV 号为 12 个字符，一千个视频的裸数据约 12 KB，压缩后更小，远超实际会达到的规模。它的更新可以很懒——插件启动时或每天拉一次即可，因为「哪些视频有内容」晚几小时同步不产生任何影响。

四个必须遵守的约束：

1. **会话内版本锁定。** 学习会话一旦创建，就固定使用当时的课程包版本与作者。中途不换，否则学生的作答记录会对不上题目，报告也无法归属。
2. **网络失败必须静默降级。** 拿不到内容时不挂载 UI，不弹错误框。学生是来看视频的，插件失败不应该干扰他看视频。这对应现有需求 11.1「插件不能破坏 B 站原生播放控制」。
3. **无课程包的视频完全不挂载。** 这条路径必须零打扰、零网络、零性能开销。
4. **SPA 跳转必须重新触发整个流程。** B 站站内切换视频时页面不重新加载，判断不能只挂在页面加载事件上。这是已经踩过的坑，见 changelog 中的 SPA 卸载修复。

**「静默」与「明确告知」必须区分清楚。** 三种情况的行为不同，混淆会造成误判为故障：

| 情况 | 行为 |
|---|---|
| 视频不在任何索引中 | 静默，不挂载，不提示 |
| 在索引中且授权有效 | 正常加载 |
| 在索引中但授权已过期 | 明确提示已过期，指向续期或联系老师 |

第三种情况下静默是错误的：学生付过费，界面什么都不出现会被判定为插件故障，进而变成老师侧的客服负担。

### 4.3 「更新」在创作者视角的表现

创作者改完并发布后，学生的实际生效时机是：

- 正在观看的学生：本次会话不变，下次打开该视频时生效；
- 尚未打开的学生：立即生效。

这个行为要在创作者后台明确写出来，不要让老师以为发布后所有人立刻切换。

## 5. 数据分层：什么放本地，什么放服务端

### 5.1 服务端（权威源）

- 创作者账号与租户信息
- 视频到课程包的索引
- 已发布的课程包内容与历史版本
- 老师订阅状态
- 学生 AI 额度账本与用量计数（权威余额，见 9.7 节）
- AI 调用代理与 prompt 模板（见 8.4 节）

### 5.2 本地 `chrome.storage.local`

- 课程包缓存（含版本号、ETag、抓取时间）
- 当前及历史学习会话（作答、尝试次数、进度、反馈，以及本次使用的 `packId`、`authorId`、`version`）
- 学生本地匿名标识 `installId`
- 按 `authorId` 索引的访问 token 列表（见 7.5 节），不存授权码原文
- AI 额度账户码（见 9.7 节）与本地缓存的额度余额；余额以服务端为准，本地仅用于显示
- 本地视频索引：已加入作者名下有讲解包的视频 ID 清单

### 5.3 绝不放在本地的东西

**AI 密钥必须留在服务端。** 插件是完全公开的可读代码，任何塞进插件的密钥都等于公开发布。调用链必须是：

```text
插件 -> 自有后端（鉴权 + 配额 + 限流） -> AI 供应商
```

后端在这一层同时解决三件事：密钥不泄露、按租户计量用量、防止单个客户或恶意调用打爆成本。这一点是硬要求，对应现有需求 11.3 和全局规则第十条。

### 5.4 发给 AI 的数据

维持现有需求第 10 节的边界不变：只发送课程与节点标识、相关课程表达、教师评价标准、学生当前回答。多租户之后额外增加一条：**请求必须携带租户标识用于计费，但不得把其他租户的任何内容带入同一个上下文。**

## 6. 反向数据流：学习数据要不要回传给创作者

这是你没有明说、但绕不开的一环。归档需求第 3.1 节把「学习证据」列为老师的核心购买理由；而一旦跨设备跨用户，这就从本地读取变成了个人数据收集问题。

三档方案：

| 档位 | 做法 | 优点 | 代价 |
|---|---|---|---|
| L0 纯本地 | 学生数据不出本机，老师只能看自己的预览 | 无隐私合规负担 | 老师拿不到学习证据，核心购买理由被削掉一半 |
| L1 学生自愿导出 | 学生点「发送学习报告给老师」，生成一份可复制的报告或一次性链接 | 无需学生账号，动作可见可控，合规压力小 | 依赖学生主动，回收率不确定 |
| L2 自动回传 | 学生凭课程码绑定身份，作答自动上传 | 老师侧数据完整，可做交付管理 | 需要隐私声明、明示同意、数据删除机制和学生身份体系 |

**建议：L1 作为默认能力，L2 作为面向机构客户的付费能力。**

理由是 L1 的工程量和合规成本都低一个量级，而它已经能支撑「老师收到了这个学生的真实作答」这个销售场景。L2 的价值主要体现在批量交付（一个老师带几十上百个学生），那恰好也是愿意付更高价的客户。

**待确认：是否接受 L2 带来的个人数据处理责任。** 这个决定影响是否需要学生账号体系、隐私政策文本和数据删除流程，是整套架构里工作量最大的分叉点，必须由你来定，不能由实现推断。

### 6.1 产品分析与学习证据分开

为改进插件而记录的**产品运行事件**，与老师需要查看的**学生学习证据**不是同一套数据：

- 产品运行事件回答「功能是否触发、是否稳定、哪里失败」，原则上只需匿名聚合；
- 学习证据回答「某名学生做了什么、结果如何」，可能包含原始回答，隐私等级更高；
- 老师只能看到自己课程的学习证据，不能接触平台聚合数据或其他老师的数据；
- 原始自由回答保留在学习会话中，不复制进通用行为分析库。

采集按阶段推进：

1. 当前 Demo 只在本地记录结构化事件，由测试者主动导出；
2. 产品化试用阶段经明确同意后，匿名上传已授权课程内的运行事件；
3. 只有 L2 自动回传或跨设备学习档案成立后，才建立账号级分析。

行为事件仅覆盖已经命中的课程。**不得记录无课程视频、完整观看历史、页面内容或无关浏览行为。** 当前只定义事件契约，不建设遥测平台和 BI 后台；最小事件集合与字段见 `doc/student-runtime.md` 11.3 节。

## 7. 多租户隔离与安全

### 7.1 权限模型

- 讲解作者只能读写自己名下的课程包；
- 授权方可以查看并下架挂在自己视频上的课程包，但不能改写别人的内容；
- 学生端一律只读；
- 服务端索引唯一决定某个视频上有哪些生效的课程包，客户端无权覆盖或新增。

### 7.2 课程包内容必须当作不可信输入

这是最容易被忽略、后果最严重的一点。

课程包由创作者编写，最终会被注入到 B 站页面中渲染。这条链路的性质是：**一方用户提供的内容，在另一方用户的浏览器页面上下文中执行。** 如果渲染时使用 `innerHTML` 或允许 HTML 片段，一个创作者就能对所有观看其视频的学生执行任意脚本，进而触及 B 站页面上的登录态。

因此：

- 课程包所有文本字段只允许纯文本，渲染一律走 `textContent`；
- 服务端在发布时做一次结构与类型校验，客户端在使用前再校验一次；
- 不允许课程包携带 URL 跳转、图片外链或自定义样式字符串，除非经过白名单校验。

样式与布局的可配置项（例如现有的字幕遮挡条）应当限定为枚举值或数值范围，而不是自由 CSS 字符串。这一约束的完整理由见 1.4 节：课程包只提供数据，不提供行为。

### 7.3 配额与滥用

按学生额度账户检查余额，并对 token、设备和上游供应商设置调用频率与成本上限。老师购买的定向额度还需校验当前 `authorId`。超限后按 8.5 节诚实降级；没有额度检查和限流的 AI 代理会让成本失控。

### 7.4 授权撤销与下架

当讲解作者不是视频方本人时，视频方必须能单方面下掉挂在自己视频上的讲解包。讲解质量差损害的是视频方的口碑，没有这个开关，第一次合作出问题就会变成纠纷。

**撤销只影响新的分发，不追回已售出的内容。**

理由：如果撤销要对已经缓存在学生本地、且学生已经付过钱的内容生效，学生端就必须频繁向服务端校验授权状态，这与第 4.2 节「尽量少发请求」的设计直接冲突。而已付费学生保留使用权本来也符合商业常识。

具体行为：

- 撤销后，服务端索引不再返回该讲解包，新学生拿不到；
- 已缓存该包的学生继续可用，直到缓存自然过期或学生主动清除；
- 视频方看到的是「已停止分发」，不是「已从所有人设备上删除」，这一点要在后台文案里写清楚，避免预期错配。

如果将来出现必须强制失效的场景（例如内容违规），再单独引入一个撤销名单机制，不要为了这个小概率场景把常规路径改成每次校验。

### 7.5 授权码与内容防扩散

#### 前提：客户端不可能做到真正的内容保护

只要内容需要在客户端渲染，客户端就能把它提取出来。插件是明文 JavaScript，`chrome.storage.local` 在 DevTools 中可读，扩展目录本身可整体拷贝。这是结构性限制，不是工程水平问题。

**明确排除的方案：把内容加密后存本地、用时解密。** 解密逻辑与密钥必须存在于客户端才能工作，读一遍代码即可获得。该方案不提高实际安全性，只增加工程量和虚假信心。同样排除代码混淆和任何形式的自建 DRM。

可行的目标只有三个：把复制成本抬到高过复制收益、让泄露可追溯、让静态内容本身不值钱。

#### 威胁模型

| 威胁 | 规模 | 单次损失 | 应对 |
|---|---|---|---|
| 学生把授权码转给同学 | 多 | 一份 | 设备绑定 + 兑换次数上限 |
| 同行批量扒取内容 | 少 | 全部 | 按需下发 + 水印 + 异常检测 |

本产品的学生来自老师的付费课程，是有信任关系的小规模群体，不是公开发售软件。威胁强度显著低于通用软件，不应按通用软件的标准投入。

#### 授权码设计：码换 token，不做静态校验

```text
老师后台为某个学生生成授权码，并自行标注发给了谁
  -> 学生输入授权码
  -> 服务端校验码，记录本次兑换
  -> 返回 token（绑定 installId、authorId、有效期）
  -> 首次兑换时发放一份平台试用 AI 额度（见 9.7 节）
  -> 后续所有请求使用 token，不再传授权码
```

授权码只承载**访问权**，不承载 AI 额度。AI 额度按 9.7 节归学生所有、跨老师通用，与授权码是两套独立的账本。授权码在 AI 计费上的唯一作用是作为试用额度的发放凭证与防刷依据。

- 插件安装时生成随机 `installId` 存于本地，token 与之绑定。
- 同一授权码在多个 `installId` 上兑换即可被检测，设置绑定数量上限，超限冻结并通知授权方。
- 多创作者场景由 token 天然隔离：token 携带 `authorId`，服务端据此决定可返回的内容。用 b1 的 token 请求 b2 的内容一律拒绝。

不采用「每次请求校验授权码」的静态方案，因为码泄露后既无法察觉也没有处置窗口。

#### 身份绑定：区分「客户端自报」与「服务端可验证」

把授权码绑定到某个身份能进一步抑制转发，但**唯一有意义的判据是身份由谁核实**。

| 做法 | 服务端可验证 | 学生摩擦 | 合规负担 | 结论 |
|---|---|---|---|---|
| 仅绑 `installId` | 是（token 由服务端签发） | 无 | 无 | 采用 |
| 老师指名发码 + `installId` | 是 | 无 | 无（身份归老师维护） | 采用 |
| 插件读取 Chrome 账号邮箱自报 | **否** | 低，但有敏感权限提示 | 有 | 不采用 |
| 自有账号或 OAuth 登录 | 是 | 高 | 有 | 暂不采用 |

**不采用读取 Chrome 账号邮箱的原因：** 通过 `chrome.identity.getProfileUserInfo()` 一类接口读到的值是插件在本地自报的，修改插件即可伪造，安全性接近于零；同时要付出敏感权限申请、安装时的权限提示、商店审核说明和持有个人信息的合规责任。付出与收益不成比例。

需要区分的是，`chrome.identity` 中走 `getAuthToken` / `launchWebAuthFlow` 的 OAuth 路径不同——token 交由服务端向身份提供方验证，属于真实认证。差别不在于用哪个 API，而在于核实发生在客户端还是服务端。

**待验证：** 上述 API 的确切权限要求与返回行为，实现前需对照当前官方文档核实，不得照本文件的描述直接编码。

#### 优先采用「老师指名发码」

本产品的学生来自老师的付费课程，**老师本来就掌握学生名单**。这是相对于面向个人销售的结构性优势：平台不需要自建身份体系去认识这些学生。

具体做法是老师在后台逐个生成授权码，并自行标注发给了谁（微信、学号、报名表编号等，形式由老师决定）。

由此获得的效果：

- 每个码对应一个具体的人，泄露可精确追溯；
- 水印直接使用老师填写的标签，威慑力强于匿名编号；
- 学生无需注册登录，摩擦为零；
- **平台不收集学生个人信息**，标签由老师维护，平台可只存哈希。这一条绕开了第 6 节中标注为最大工作量分叉点的隐私合规问题。

引入学生账号的时机应当是需要 L2 自动回传或跨设备同步学习进度时——那时账号是为了功能而建，不只是为了防转发，投入才成立。

#### 必须配套的解绑机制

绑定 `installId` 之后，学生换电脑、重装浏览器或清理数据都会导致绑定失效。**没有重置手段，这会直接变成老师侧的客服负担，并转嫁给平台。**

必须至少提供其中一项：

- 老师后台可重置某个授权码的设备绑定；
- 允许单个授权码绑定少量设备（覆盖「家里 + 公司」这类正常需求）。

该机制与防转发措施必须同时上线，不能后补。

#### 多创作者授权并存

A 从多个老师处购课时，逐个输入各自的授权码即可，无需任何额外机制。本地形成一个按 `authorId` 索引的 token 列表，界面上提供「我的课程」用于查看已加入的老师并添加或移除。

四条约束：

1. **学生只接触授权码，不接触 token。** 界面上不出现 token 字样，也不提供复制 token 的入口——否则设备绑定形同虚设。
2. **请求只携带当前视频对应的那一个 token。** 本地虽然同时持有多个凭证，但不得在一次请求中一并发送，避免让某一方的服务调用看到其他方的凭证。
3. **学习会话必须记录归属。** 除现有的 `lessonId` 外，会话需记录本次实际使用的 `packId`、`authorId` 和 `version`。A 同时是多位老师的学生，缺少这些字段会导致学习报告发给错误的老师，且事后无法从会话记录反推。
4. **撞车必须有确定性规则。** 若 A 从两位老师处购买了同一视频的讲解，第一版不提供选择界面，但必须按固定规则择一（例如取加入时间最早的作者），并在会话中记录实际使用的包。规则取哪一条都可接受，不确定则不可接受——否则同一学生两次打开同一视频可能得到不同老师的题目，数据将无法解释。

#### 四项轻量措施（按性价比排序）

1. **按需下发。** 学生打开哪个视频才下发哪个包，不在加入课程时下载整套。零额外成本，仅是设计选择。本地被拷时只泄露已学部分，想扒全套必须逐节真实播放。
2. **AI 反馈与学习报告必须走服务端。** 这一条本来就因密钥托管而必须成立（见 5.3 节）。附带效果是拷走的静态内容缺失自由回答反馈和报告，只剩确定性题目。
3. **下发内容嵌入学生标识。** 增加一个字段即可，泄露后可追溯来源。可见水印（例如「本课程由 XX 授权给学员 #1234」）的威慑力强于隐藏水印。
4. **服务端异常检测。** 关注同一 token 短时间内的多 IP 请求、同一授权码的异常兑换次数。起步阶段人工查看日志即可，不建监控系统。

#### 结论

采用上述措施把随手分享的成本抬起来即可，**不向 DRM 方向投入任何工程量**。

依据 `doc/lessons.md`「Do Not Treat Copyable UI as the Asset」，以及归档需求 3.1 节对购买动机的历史判断：老师售卖的价值在批改、答疑和学习证据，不在题目文本。一份被拷走的静态课程包无法产生 AI 反馈和学习报告，实际价值远低于表面。

在第一个付费客户尚未验证之前，防盗版投入的产出比为负。若将来真的出现大规模扒取，届时掌握的信息也远多于现在。

## 8. 学生端能力分层与 AI 位置

### 8.1 按成本分三层

该分层同时是定价的分界线。

| 层 | 条件 | 边际成本 | 学生端能力 |
|---|---|---|---|
| L0 | 完全本地 | 零 | 视频识别与会话启动、Avatar 状态、定时暂停、选择题、填空题、重试/跳过/继续、进度显示、字幕遮挡、本地会话存储 |
| L1 | 需要网络，不需要 AI | 极低（请求数与带宽） | 授权码兑换与 token 管理、本地视频索引同步、课程包拉取与版本更新、学习报告导出给老师 |
| L2 | 需要 AI | 真实变动成本 | 自由回答反馈、学习总结中的语言建议 |

L0 与 L1 可以包含在订阅内，L2 必须单独计量。

对照归档需求 6.1 节的历史编号：L0 覆盖 S01–S05、S07、S08 的进度部分和 D01；L1 全部为多创作者阶段新增；L2 覆盖 S06 和 S08 的语言建议部分。

字幕遮挡已于 requirements v0.4 补录为 S09。

### 8.2 是否使用 AI 等同于是否启用自由回答节点

AI 用量与节点类型一一对应：

- 选择题与填空题为确定性判断，不调用 AI（当前规则见 `doc/requirements.md` 第 5 节）；
- 自由回答节点必须调用 AI，否则无法评价。

因此「这节课要不要用 AI」就是「要不要启用自由回答节点」，由老师在编辑器里决定。全部使用选择题和填空题的课程不产生任何 AI 调用。

按 9.7 节，老师默认不承担学生的 AI 用量费用，因此启用自由回答首先是**教学决定**。老师只有在希望承诺「本课含 AI 反馈」时，才可选购定向额度，这属于独立的商业配置。

该映射同时使调用量可估算：节点数 × 学生数 × 每节点重试上限即为调用上限。这对平台核算试用额度成本和对学生说明额度消耗速度都有用。

### 8.3 AI 用量的三个来源

1. **自由回答反馈**：每次提交计一次，含重试。主要开销。
2. **学生学习总结**。
3. **老师报告中的薄弱点与后续建议**。

第 2 项与第 3 项**必须由同一次调用产出**。这是归档需求中老师报告与学生总结数据同源的远期设想，不是当前要求。

**报告必须生成一次后缓存。** 每次打开报告都重新调用 AI 会造成成本失控，且违反同一会话事实一致的要求。

### 8.4 AI 能力的位置

调用链见 5.3 节：插件 → 自有后端 → AI 供应商。后端职责：

1. 校验 token；
2. **检查额度（必须在调用 AI 之前，不得先调用后扣减）**；
3. 限流；
4. 组装 prompt；
5. 校验输出结构后才允许渲染。

**prompt 模板必须存放在服务端。** 理由不限于安全：`doc/lessons.md` 已将 vertical prompt templates 列为本产品的持久资产，而插件代码完全公开可读。把 prompt 放进插件等于公开发布核心资产。此项与密钥必须留在服务端属于同等强度的要求。

**后端应通过兼容接口层调用上游供应商，而不是直接绑定某一家。** 收益是可比价、可按场景在高价与低价模型之间切换、上游涨价时可快速迁移。这与 9.6 节「上游模型价格会变动」的独立计价理由直接对应。该抽象层工程量很小，宜早做。

### 8.5 额度耗尽的降级行为

额度耗尽时**降级而非拒绝服务**，且降级必须诚实。此项是归档需求 S06「AI 失败时不得用固定模板冒充针对该学生的个性化反馈」的直接延伸：

- 明确提示「智能反馈额度已用完」，并给出充值入口（额度归学生所有，见 9.7 节）；
- 保留学生原始回答，允许继续播放；
- 不得输出假装个性化的模板反馈；
- 报告中记录「未生成 AI 反馈」，不得补写虚构评价。

充值入口的呈现必须节制：这是学生自愿加购的通道，不是付费墙。学生不充值也必须能完整看完课程并完成所有确定性题型。

### 8.6 创作者档位映射

分层原则：**免费档要让创作者跑通完整闭环（否则他无法判断价值），付费档卡在规模和交付能力上。**

| 能力 | 免费 | 基础版 | 专业版 | 机构版 |
|---|---|---|---|---|
| 课程包数量 | 1 | 少量 | 较多 | 不限 |
| 互动节点数 / 课程 | 3 | 不限 | 不限 | 不限 |
| 确定性题型（选择、填空） | 有 | 有 | 有 | 有 |
| 启用自由回答节点 | 有 | 有 | 有 | 有 |
| 学习报告（L1 自愿导出） | 有 | 有 | 有 | 有 |
| 学习数据自动回传（L2） | 无 | 无 | 无 | 有 |
| 多老师协作 | 无 | 无 | 无 | 有 |
| 品牌定制 | 无 | 无 | 有 | 有 |
| 自带 API Key | 无 | 无 | 无 | 可选 |

**AI 额度不出现在创作者档位中**，因为按 9.7 节它记入学生账本，与老师的订阅档位无关。各档位一律允许启用自由回答节点——限制老师启用它没有意义，老师默认并不为此付费。

老师若希望承诺「本课含 AI 反馈」，可另行购买定向额度（见 9.7 节），这是与订阅档位无关的独立采购。

表中的档位划分是结构建议，**每档的具体数量阈值没有依据，属于占位，必须由真实客户访谈确定后再填。**

## 9. 收费模式

### 9.1 四种计费口径对比

| 口径 | 优点 | 缺点 |
|---|---|---|
| 按创作者订阅（月/年） | 收入可预测，客户容易理解 | 与实际价值脱钩，重度用户和轻度用户同价 |
| 按学生数 | 与创作者的收入规模挂钩 | 学生数难以核实，且学生数增长会让老师抗拒推广 |
| 按 AI 用量 | 与成本对齐，毛利安全 | 账单不可预测，客户普遍反感 |
| 一次性改造服务费 + 订阅 | 前期现金流好，符合老师「改造课程」的心理模型 | 不可规模化，服务交付占用人力 |

### 9.2 建议路径

**第一阶段（前若干个客户）不做自助订阅。**

采用「人工改造服务费 + 手动开通账号」：你帮老师把一节课改造好，收一次性费用，同时手动开通后台。这样做的三个理由：

1. 现有需求文档第 14.2 节的商业验证标准本来就是「老师愿意提供真实课程、同意试用、愿意讨论付费金额」——这三件事都不需要在线支付系统。
2. 支付、订阅、发票、退款是一整套工程，在愿付价格尚未验证时投入，是典型的过早优化。
3. 人工交付的过程本身会暴露真实的定价锚点和功能优先级，这些信息比一个自助付费页面值钱得多。

**第二阶段**在收到重复购买、且改造流程被 SOP 化之后，再上自助订阅。此时按创作者订阅作为 L0/L1 主口径；AI 继续使用独立预付额度账本，避免把变动成本混进老师订阅。

### 9.3 定价还缺的证据

在填入任何具体数字之前，至少需要：

- 目标老师现有课程的客单价与学生规模；
- 老师当前在答疑和批改上的时间投入；
- 老师为同类工具（社群工具、作业系统、直播工具）已经在付的钱；
- 单个学生完成一节课的 AI 调用成本实测值。

第四项可以在 Phase 4 实现自由回答功能后直接测出来，前三项需要销售访谈。**在这四项拿到之前，任何定价数字都是编的。**

### 9.4 视频方与讲解方的分成

当视频方把讲解交给别人做时，两者之间存在分账关系。

**建议第一阶段平台不碰钱：分成由双方私下签约，平台只提供对账数据。**

理由：平台一旦代收代付，就要处理资金流、发票、税务、退款和纠纷仲裁，工程量和合规成本比整个产品本身还大。而在合作对数只有个位数时，双方直接签合同完全够用。

平台需要提供的对账数据：某个讲解包由谁授权、覆盖多少学生、产生多少次使用。有了这些，双方自己就能算清楚。

### 9.5 关于「卖版权」的效力边界

需要区分三种强度不同的东西，不要混为一谈：

1. **讲解包本身的著作权是成立的。** 题目、评价标准、讲解文字是新创作的内容，归讲解作者，可以授权和转售。
2. **「在某个视频上挂讲解」这项权利的法律基础存疑。** 插件是在用户自己的浏览器中做叠加渲染，不复制、不转播、不下载视频，用户观看的仍是原平台的原片。这与制作衍生作品不是同一件事。**此项必须取得正式法律意见后才能写进合同或对外宣传，本文件不提供法律结论。**
3. **实际可交易的是平台规则加合同。** 平台可以规定「一个视频上的讲解位由授权方决定谁能占」，这条规则在平台内有效，但效力来自用户都在平台上，不来自法律。因此它的价值与平台规模严格绑定：规模小的时候绕过它几乎没有成本，这项授权也就卖不上价。

**战略含义：** 讲解层与视频解耦确实打开了供给面（讲解者不必拥有视频，视频方也不必自己下场做互动课），但它同时把产品从单边 SaaS 变成了双边市场。双边市场需要供需同时启动，难度显著更高。在第一个付费客户尚未验证之前，不应把撮合和分成当作产品方向投入开发；按第 11 节，现在只在数据结构上留出 `ownerId` / `authorId` 的位置即可。

### 9.6 AI 额度独立计价

**AI 用量与订阅分开计价，采用预付额度，不做后付账单。**

- 设硬上限，额度耗尽时按 8.5 节降级，而不是拒绝服务或继续扣费；
- 预付消除账单不确定性，同时保留用量计费的成本对齐优点。这是对 9.1 节「按 AI 用量计费的账单不可预测、客户普遍反感」的针对性解法。

独立计价的四个理由：

1. 成本结构不同——L0/L1 是固定成本，L2 是变动成本，混入同一价格必有一方吃亏；
2. **上游模型价格会变动**，独立计价才能只调 AI 价格而不动订阅价格；
3. 老师可以完全不用 AI（见 8.2 节），不应为此付费；
4. 额度可作为试用或促销赠送，不影响订阅收入的账面。

计费单元取「一次 AI 调用」，而非「一名学生」或「一节课」，因为只有调用次数与真实成本线性对应。对外展示时可换算成更易理解的口径（例如「约可完成 N 次自由回答练习」），但计量基础必须是调用次数。

**付款方见 9.7 节：AI 额度由学生购买，老师只付订阅。**

### 9.7 统一收费架构：老师付订阅，学生付 AI 额度

**老师为 L0/L1 能力支付订阅。AI 额度默认由学生购买并跨所有老师通用；老师可选地为自己的课程配给定向额度，以便把 AI 作为课程卖点。**

| 谁付 | 付什么 | 对应能力 |
|---|---|---|
| 老师 | 订阅 | L0/L1：课程包托管、分发、更新、报告 |
| 老师（可选） | 定向 AI 额度 | 为自己的课程承诺「含 AI 反馈」 |
| 学生 | 通用 AI 额度 | L2：自由回答反馈、总结中的语言建议 |
| 平台 | 试用额度 | 获客成本 |

#### 前提：一个学生对多个老师

本模型的价值完全建立在这个前提上。如果一个学生只有一个老师，额度归谁管理没有区别。

**跨老师通用消除了额度碎片化。** 若额度绑定在老师身上，学生从 b1 处获得的额度只能用于 b1 的课程，从 b2 处获得的只能用于 b2 的课程。结果是每处都剩一点、都用不完、也无法合并。学生的老师越多，浪费越严重——而这正是目标场景。

#### 战略含义：老师门槛降为零

老师不需要垫资、不需要批发、不需要核算 AI 成本、不承担库存风险。他只做课程，在课程中加入自由回答节点即可让学生试用。

对老师的表述是：**零成本为自己的课程加上 AI 能力。**

同时老师成为免费的分发渠道：他提供试用，学生体验到价值后自行充值。获客成本由老师的课程销售承担。

**AI 由此从「老师的成本」转变为「学生的消费」。** 这是本模型与 9.8 节批发方案的根本差异。

#### 代价：需要一个轻量的学生级标识

跨老师通用的额度必须绑定到学生级别的标识上，否则无法确定额度归属。这与 7.5 节「平台不收集学生个人信息」存在张力。

**采用礼品卡模型作为最轻解法：** 学生充值后获得一个额度账户码，由学生自行保管；更换设备时输入该码恢复额度。不需要注册、密码、手机号或邮箱。

代价是账户码丢失即额度丢失。这在预付卡的心理模型中可接受。如需更高可靠性，可提供**可选**的恢复方式绑定，从而渐进接近账号体系，而不是一次性建立账号体系。

#### 试用额度的防刷由授权码天然解决

试用额度由平台承担。防止无限领取的机制现成可用：**试用额度挂在授权码上，每个授权码首次兑换时发放一次。**

授权码由老师发放、数量有限、可追溯到具体学生（见 7.5 节），因此不需要为试用额度另建防刷体系。

#### 老师的推广动力来自课程溢价，不是分成

**若老师完全不能从 AI 获益，他就没有向学生推广该功能的动力**，而老师是通往学生的唯一渠道。这是必须解决的问题。

解法不是充值分成，理由是**分成是他人款项的一小部分，而课程溢价由老师自己定价且全额归他**，后者的量级更大。AI 反馈同时提高课程转化率与感知价值，这是归档需求 3.1 节记录的远期购买动机。

但要让这条路成立，老师必须能够承诺「**本课包含 AI 一对一反馈**」。纯学生自购模式下他无法承诺，卖点也就不存在。**因此必须允许老师可选地为自己的课程配给定向额度。**

| 老师类型 | 做法 | 收益来源 |
|---|---|---|
| 以 AI 为卖点 | 为课程配给定向额度，成本含入课程价 | 课程溢价与转化率提升 |
| 不投入 | 不配额度，学生使用平台试用额度体验 | 零成本，学生自行加购 |
| 机构或技术型 | 自带 API Key（见 9.8 节） | 成本自控 |

由老师自行选择。**不设充值分成**：课程溢价这条路更强，且不引入任何激励错位。

如后续确需额外推力，可增加**首充推荐奖励**——挂在学生首次充值这一转化动作上，不挂在后续消耗上。挂首充鼓励老师让学生用起来，挂消耗则鼓励老师让学生多消耗。

#### 原有激励错位在本结构下已消失

上一版方案担心的「老师压低额度以迫使学生充值」在本结构下不成立：**平台发放的试用额度由授权码触发，老师无法干预。**

老师唯一的选择是是否为自己的课程配给定向额度，而不配额度对他没有好处——那样他就失去了可宣传的卖点。**激励方向因此是正向的：越想获得课程溢价，就越会多配额度。**

#### 保留的约束：调用必须归属到具体课程

即使额度归学生所有，**每次 AI 调用仍须记录发生在哪位作者的哪节课上**。老师报告需要据此了解学生在其课程中的表现。此项与 7.5 节「学习会话必须记录 `packId`、`authorId`、`version`」是同一项要求。

#### 三种额度与扣减优先级

| 额度类型 | 来源 | 使用范围 |
|---|---|---|
| 试用额度 | 平台发放，授权码首次兑换时触发 | 跨老师通用 |
| 定向额度 | 老师为自己的课程配给 | 仅限该老师的课程 |
| 通用额度 | 学生自行充值 | 跨所有老师通用 |

**扣减顺序：试用额度 → 当前课程的定向额度 → 学生通用额度。**

两条理由：

1. 免费的先用完，避免学生付费购买的额度在还有免费额度时就被消耗；
2. 定向额度优先于通用额度，**否则学生自购的通用额度会被某位老师的课程白白消耗，而该老师配给的额度闲置**，学生会认为受到损失。

老师配给但未被消耗的定向额度同样是平台的纯利润（款已收而 AI 成本未发生），因此同样不应设置短期限（见 9.8 节保留的洞察）。

### 9.8 已评估的替代方案

#### 方案一：授权码携带额度、老师批发转售（部分保留）

做法是授权码同时承载访问权与 AI 额度，老师从平台批发、含在课程价格中转售，差价为其收益。

**未被采用的部分：** 把额度绑定在授权码上会造成跨老师的额度碎片化——学生在每位老师处都剩一点、都用不完、也无法合并（见 9.7 节）。同时它强制所有老师垫资，与降低老师门槛的目标相反。

**被 9.7 节吸收的部分：** 「老师出钱为自己的课程配给额度」这一动作本身是必要的，它是老师能够承诺「本课含 AI 反馈」、从而获得课程溢价的前提。9.7 节将其保留为**可选的定向额度**，而不是强制的批发义务，且额度记入学生账本而非授权码。

**保留的两项洞察：**

1. 同一笔支出，表述为「你要为 AI 付费」时老师抗拒，表述为「你可以批发加价转售」时老师接受。表述方式影响成交，这一点在 9.7 节改为「零成本加上 AI 能力」后同样适用。
2. **未被消耗的预付额度是纯利润**——钱已收而 AI 成本未发生。因此额度不应设置短期限。此结论在 9.7 节的学生充值模型下继续成立。

#### 方案二：老师自带 API Key（保留为机构选项）

**仅面向机构或具备技术能力的客户，不作为默认路径。** 三项代价：

1. 绝大多数目标老师不会开设 API 账号、管理密钥或查看用量，摩擦极高。
2. 平台代为保管他人凭证，泄露后果是客户被盗刷，责任重大。
3. **模型不一致会使 prompt 模板失效。** prompt 是针对特定模型调优的核心资产，老师更换模型后反馈质量不可控，而学生的负面评价仍会归于 KnownMap，且平台无法查看日志排查（密钥不属于平台）。

因此启用自带 Key 时必须明确声明：**反馈质量不在平台承诺范围内。**

使用自带 Key 时不走额度账本，但仍需记录调用次数，用于老师侧展示与故障排查。

### 9.9 To C 路线：只预留，不作为当前业务线

KnownMap 的当前商业定位是**小 B 优先的 B2B2C**：

- 老师是购买者、课程配置者和交付者；
- 学生是插件使用者，但不是现阶段的主要获客对象；
- 平台通过解决老师的课程差异化、批改、答疑和学习证据问题获得收入。

因此不照搬 Immersive Translate、Trancy、Language Reactor 等 To C 浏览器扩展的「免费版 + Pro」路径。当前不建设独立 To C 产品、不设计学生 Pro 订阅，也不让该设想改变 Phase 1 或老师端平台的优先级。

保留 To C 的含义只包括两点：

1. 数据结构允许跨老师的学生公共能力，例如通用 AI 额度、错题重练、生词收藏和学习档案；
2. 通过行为事件验证是否出现真实的自然使用、跨课程留存和学生付费需求。

未来只有在这些证据成立后，才重新评估 To C：

- 学生在脱离老师督促后仍持续使用；
- 公共学生工具产生跨课程留存，而不是一次性尝鲜；
- 学生愿意为明确价值付费，且获客成本不依赖老师补贴；
- To C 不削弱老师的课程价值与渠道关系。

当前竞争重点不是提前堆出更完整的功能框架。题卡、字幕和 AI 按钮容易复制；更难复制的是课程改造 SOP、稳定组件 schema、老师交付闭环、真实案例、教学 prompt 与质量基线，以及授权、分发和学习证据体系。

## 10. 部署形态

### 10.1 组成部分

| 部件 | 形态 | 说明 |
|---|---|---|
| 学生端插件 | Chrome MV3 扩展 | 内容脚本 + Service Worker，只保留取数与渲染 |
| 创作者后台 | 独立网页应用 | 不做成插件页面 |
| 后端服务 | HTTP API | 课程包分发、租户鉴权、AI 代理、用量计量 |
| 数据库 | 关系型 | 租户、课程包、版本、授权、用量 |

**创作者后台应当是网页而不是插件页面。** 老师需要在任意一台电脑上改课程，不应该被迫长期依赖插件页面；而且网页版才能做团队协作、支付页面和营销落地。当前 D0 使用 localhost 基础网站，通过严格白名单的消息桥写入扩展本地配置；产品化后改为网站调用后端草稿、发布、订阅与支付 API。桥接层只是 Demo 过渡方案，不扩展成正式后端协议。

### 10.2 插件分发

初期采用定向分发（打包后直接给到合作老师，或使用商店的非公开链接），验证后再正式上架 Chrome Web Store。

上架需要提前准备的事项：权限说明（当前 manifest 只申请了 `https://www.bilibili.com/*` 的宿主权限，多平台后会扩大，扩大权限会显著增加审核难度）、隐私政策、数据用途声明。审核有不确定的周期，不应该排在销售验证的关键路径上。

### 10.3 后端技术栈

按全局规范（`agent/coding/AI编程全局规范/GLOBAL_DEV_WORKFLOW.md`），Python/FastAPI 是默认后端选型，对应专项规范 `PYTHON_FASTAPI_DEV_STANDARD.md`。涉及密钥、鉴权和外部输入，另需遵守 `SECURITY_CODING_STANDARD.md`；涉及 LLM 调用，另需遵守 `AI_LLM_INTEGRATION_STANDARD.md`。这三份专项规范在实际开工时才需要读取。

### 10.4 起步规模

第一版后端只需要三个端点：按视频 ID 查课程包、创作者读写自己的课程包、AI 反馈代理。这个规模用单台小服务器即可承载，不需要在起步阶段引入容器编排、消息队列或多区域部署。

## 11. 与当前 Phase 计划的关系

本方案对应 `doc/dev-plan.md` 中「Deferred」列出的内容，不改变 Phase 1–5 的执行顺序。

当前阶段**不需要**为多租户做任何抽象、扩展点或兼容层。按全局规范「开发从简」的要求，未确认的需求不应产生代码。

只记录两处几乎零成本、但以后返工代价明显的注意点，供实现到对应位置时参考，**不构成现在就要改代码的要求**：

1. 课程包的数据结构里，`id` 与视频标识的关系应保持清晰可分离。现有 `design.md` 第 4 节的 `{ id, videoId, ... }` 结构已经满足，后续加 `ownerId`、`authorId` 和 `version` 是纯增量。当前 Demo 天然处于 `ownerId == authorId` 的形态，不需要为「授权给别人做」提前写任何代码。
2. 课程包的读取入口应保持单一。只要学生运行时始终通过一个函数拿配置，将来把「读本地常量」换成「读缓存或拉服务端」就是替换一个实现，而不是全局搜索改写。
3. 1.4 节的「课程包只提供数据，不提供行为」应当从现在开始遵守。它不增加任何工作量——反而更省事——但一旦某个版本开了自定义样式或标记的口子，收回来的成本极高。节点遇到无法识别的 `type` 时跳过并继续播放，也应当在实现节点状态机时一并做掉，成本接近于零。

## 12. 性能约束

以下均为基于设计的推断，**尚无实测基线**。当前代码只在单个视频上运行过，任何性能结论在测量之前都不成立。

### 12.1 取数路径的开销可以忽略

多创作者带来的额外成本很小：本地视频索引是 ID 集合，10 位作者各 100 个视频也仅 1000 条，用 Set 查找为 O(1)。主要成本是一次 `chrome.storage.local` 异步读取（毫秒级），且 B 站站内切换视频不重建 content script，索引可驻留内存，后续切换为纯内存查找。

第二、三层仅在索引命中时触发，属于极少数情况。**第三层的网络请求必须异步，不得阻塞视频播放路径。**

### 12.2 三处真实风险

**1. content script 注入到了所有 B 站视频页。**

`src/manifest.json` 匹配 `https://www.bilibili.com/video/*`，因此每个视频都会注入并执行全部脚本与样式，而其中绝大多数视频与课程无关。两项改进方向：

- CSS 目前无条件注入。未匹配任何元素的样式表仍会参与页面样式计算，应改为确认挂载后动态注入。
- 重量级模块（mascot canvas、题卡渲染）不应随 content script 一起解析，应按需加载。**无关视频的代码路径必须在任何 DOM 操作和监听器注册之前退出。**

**2. 时间监听属于高频路径。**

`timeupdate` 回调中只允许 O(1) 数值比较，不得进行 DOM 查询、`storage` 读写或数组遍历。这对应归档需求 11.2 节「时间监听不得造成视频明显卡顿」的性能原则。

同时，SPA 跳转若卸载不干净会造成监听器堆积——连续观看数十个视频即累积数十个 `timeupdate` 监听。该问题已踩过一次（见 changelog 的 SPA 卸载修复），多创作者场景下 A 的浏览路径更长，触发概率更高。

**3. 本地存储只增不减。**

学习会话持续累积，多创作者、多课程、多次重练会加速增长。需要定义会话保留期限与课程包缓存的淘汰策略。此项当前无需处理，但长期不处理会表现为「插件突然无法写入数据」这类难以排查的故障。

### 12.3 需要实测的项目

1. 在没有课程包的普通视频上，插件带来的额外 CPU 与内存占用。
2. `timeupdate` 的实际触发频率与单次回调耗时。
3. 连续切换数十个视频后，事件监听器与 DOM 节点数量是否增长。
4. 从索引命中到题卡渲染完成的端到端耗时。
5. `chrome.storage.local` 的实际配额上限（需核对当前官方文档，不采用记忆值）。

## 13. 待确认清单

以下问题不阻塞当前 Phase 1–3，但会实质改变产品化阶段的架构与工作量，必须在对应阶段开工前由决策者拍板：

1. 是否接受 L2 自动回传带来的个人数据处理责任（决定是否需要学生身份体系与隐私合规工作）。
2. 授权方如何证明自己拥有某个视频（决定能否开放自助注册）。
3. ~~是否支持 B 站以外的平台~~ **已拍板：** D0/D1 只做 B 站；D1 验证后增加 YouTube 作为第二个 `PlayerAdapter`；其他平台等真实老师课程来源再排序。多语言界面、课程语言体系和多地区支付/合规当前完全不做，也不预留 schema 字段。
4. 同一视频出现多方主张授权权时的处理规则。
5. 免费档的具体额度（决定获客成本与滥用风险）。
6. 是否真的要做「视频方授权他人讲解」这条线，还是长期维持 `ownerId == authorId`（决定是否要建授权、对账和下架体系）。
7. 单个授权码允许绑定的设备数量，以及重置由老师自助还是走平台人工（决定客服成本落在谁身上）。
8. 授权码的有效期与到期行为：完全停用，还是保留已缓存内容但停止更新与 AI 反馈（与 9.2 节的收费路径绑定，需在确定收费模式后决定）。
9. 单个自由回答节点允许的重试上限，以及每个授权码首次兑换发放的试用额度大小（两者共同决定平台的获客成本敞口，需在实测单次调用成本后确定）。
10. S09 的教学目的表述是否准确（补录定义时依据实现行为推断为「遮挡字幕以训练听力」，需由课程作者确认）。
11. 学生充值通道何时上线，以及是否先用人工发卡验证需求（决定何时需要支付商户资质与退款流程，见 9.7 节）。
12. 是否开放老师自带 API Key，以及开放给哪一档客户（决定是否需要建立密钥托管与「质量不予承诺」的条款，见 9.8 节）。
13. 额度账户码丢失是否提供找回，以及是否提供可选的恢复方式绑定（决定平台是否开始持有学生联系信息，见 9.7 节）。
14. 是否需要首充推荐奖励作为老师的额外推广激励，以及奖励是否只挂首次转化（见 9.7 节。默认不做，仅在课程溢价不足以驱动老师推广时启用）。
15. 产品化匿名事件的保留期限、聚合粒度与删除入口（事件范围已确定，具体期限需在隐私政策和试用方案确定时拍板）。

以下事实尚未验证，得出结论前必须先取得证据：

1. B 站视频页面上 UP 主标识的稳定获取方式（需要在代码中实测）。
2. 单个学生完成一节三节点课程的实际 AI 调用成本（Phase 4 后可实测）。
3. 「在他人视频上叠加讲解层」的法律定性，以及「出售该权利」是否有效（需要正式法律意见，不能由本项目自行判断）。
