# 未来功能想法记录

用途：记录已经出现、但还没有进入正式需求和设计流程的功能想法。

这里的内容是产品想法池，不是当前开发指令，也不是接口、数据结构或验收标准的最终真源。某个想法真正进入开发前，仍需补充正式需求、设计、权限边界、数据迁移和验收方案。

## 记录规则

- 每个想法保留提出背景、目标、范围、暂不解决的问题和可能的下一步。
- 已经完成的阶段要标明“已实现”；未完成的扩展要单独列出，避免把想法误认为当前能力。
- 涉及文件格式、权限、数据迁移、学生数据或外部平台时，必须记录明确边界。
- 想法被接受后，应回链到正式需求文档或设计文档；正式文档与本文件冲突时，以正式文档为准。

## 想法 001：课程导入与导出

状态：第一期已实现管理员代操作；教师自助权限和教师类型策略仍待后续设计。

### 背景

课程内容可能需要在不同教师工作区之间迁移、备份或由管理员协助恢复。课程结构、节点配置和节点辅助资料不能依赖数据库手工复制，也不能把学生交付课程包直接当成教师编辑文件使用。

### 想法目标

提供一个自描述的 `.kmcourse` 课程文件，让有权限的操作者可以：

1. 导出教师已经保存的课程草稿或明确的发布版本；
2. 导入文件前查看课程、课节、节点和资源摘要；
3. 确认后在目标教师工作区创建一门新的课程草稿；
4. 在导入失败时不留下半门课程、孤立资源或错误的课程引用。

### 课程包内容边界

课程包底层使用 ZIP，包含 `manifest.json` 和 `assets/*.bin`。

应当保存：

- 课程和课节结构；
- B 站视频的播放引用，包括 BVID、分 P、CID 等；
- 节点的文字、互动配置、触发时间和展示配置；
- 节点讲解使用的图片、音频和辅助视频二进制；
- 资源 MIME、字节数、SHA-256 和来源类型；
- 教师已经保存的字幕；未保存的页面状态不导出。

明确不保存：

- 课程主视频，即 B 站视频文件本体；
- 密码、会话、授权码、学生回答和学习进度；
- 学生插件使用的本机状态；
- 原课程或发布版本的数据库身份作为目标对象的直接主键。

导入时课程、课节、节点和资源都要生成新的平台身份，并重写节点中的资源引用。课程主视频仍由 B 站引用决定，不由课程包下载、托管或转移。

### 业务流程

```text
选择目标教师
  → 查看课程摘要
  → 选择草稿或发布版本导出

上传 .kmcourse
  → ZIP / JSON / Schema / 大小校验
  → 节点结构和资源完整性校验
  → 显示预览摘要
  → 管理员确认
  → 生成新资源身份
  → 创建新课程和新草稿
  → 原子提交并记录审计
```

导入不覆盖原课程、不自动发布、不生成授权码。预览接口只读；确认导入失败时回滚数据库并清理已经写入的资源。

### 权限想法

第一期只在管理员界面提供课程包管理区，管理员必须先明确选择目标教师，服务端再次校验教师、课程、发布版本和资源归属。

未来可以按教师类型或服务端 capability policy 决定：

- 哪些教师可以导出自己的课程；
- 哪些教师可以导入课程包；
- 是否允许导入发布版本；
- 是否需要管理员审批或操作审计。

权限不能只靠前端隐藏按钮实现，也暂不为了这个想法新增 `teacher_type` 数据库字段。

### 待后续设计的问题

- 教师类型的真实数据来源和能力配置方式；
- 教师自助导入时的来源教师、内容权利和跨工作区边界；
- 课程包格式的长期版本兼容、升级和失效策略；
- 大型节点辅助视频的上传、下载、断点续传和存储配额；
- 导入资源的生命周期清理、重复资源去重和恢复机制；
- 是否允许只导出课程草稿中的部分课节或节点。

## 想法 002：班级授权码与老师代学生领取课程

状态：想法记录，当前不实现；需要重新设计授权、学生身份和课程交付流程。

### 背景

当前授权码主要面向单个领取动作。未来老师可能按照自己的班级或学生群体批量组织课程，并为一个班级生成可供自己学生使用的授权码。学生取得课程的方式也可能不再只有“学生自己输入授权码”这一条路径，还可能由老师协助完成课程分配或领取。

### 想法目标

让老师能够围绕一个班级管理课程交付：

1. 创建或选择自己的班级；
2. 为班级绑定一门或多门课程，以及允许领取的课程版本或范围；
3. 生成班级授权码、邀请链接或其它受控入口；
4. 查看哪些学生已经领取、待领取或领取失败；
5. 在学生不方便操作时，由老师发起协助流程，但不能把课程错误地领取到老师自己的浏览器或身份下。

### 可能的学生进入路径

#### 路径 A：学生自行输入班级授权码

```text
老师创建班级并绑定课程
  → 生成班级授权码
  → 学生在自己的设备输入授权码
  → 服务端校验班级、课程、有效期和领取资格
  → 课程进入该学生自己的课程库
```

#### 路径 B：老师帮助学生完成分配

```text
老师选择班级中的学生或待分配名额
  → 老师确认要分配的课程
  → 服务端生成学生待领取/已分配记录
  → 学生打开自己的课程入口完成安装
  → 课程进入学生自己的课程库
```

“老师帮学生完成”需要进一步定义具体含义：可以是老师只完成课程分配，也可以是老师代为创建领取记录，但不应默认让老师持有学生的本机证明、登录凭证或学习状态。无论采用哪种方式，最终课程都必须进入学生自己的设备和本机课程库。

### 可能的数据结构

以下只是待讨论的对象，不是当前数据库设计：

```text
Classroom
  ├── teacher / workspace
  ├── name / status
  └── members

ClassMembership
  ├── classroom
  ├── student reference or pending seat
  ├── status
  └── joined / revoked time

ClassGrant
  ├── classroom
  ├── course or release scope
  ├── reusable code or invite
  ├── expiry / quota
  └── revoked time

StudentCourseAssignment
  ├── class membership
  ├── course / release
  ├── self-claimed or teacher-assisted
  └── pending / installed / failed status
```

当前学生端以本机学习标识为主，未形成完整的学生账号和班级花名册模型。因此，在真正设计前必须先决定：班级成员如何识别、老师如何确认某个学生、跨设备如何避免误领，以及“老师代操作”是否需要学生确认。

### 需要重新设计的流程

- 班级创建、编辑、归档和教师归属；
- 班级授权码是一个班级复用，还是每个学生一次性使用；
- 班级码是否允许绑定多门课程、多个发布版本或限定课节；
- 领取人数上限、有效期、撤销、换码和重复领取规则；
- 学生自行输入授权码与老师代分配的状态是否使用同一套课程安装流程；
- 老师是否能看到学生姓名、领取状态或失败原因，以及这些信息的最小化原则；
- 学生换设备、清除本机数据或重复领取时如何恢复资格；
- 课程发布新版本后，班级中的学生是否自动获得更新资格；
- 班级解散、学生退出和授权撤销后，学生本机已安装课程如何处理。

### 权限与安全边界

- 班级只能由所属老师或管理员管理，老师不能读取其它老师的班级和学生关系；
- 班级授权码不能替代学生身份，也不能让老师读取学生密码、本机证明、回答或学习进度；
- 老师代分配必须明确记录操作者、目标学生或名额、课程版本和结果；
- 班级码泄露时应能停用、轮换或限制影响范围；
- 服务端必须重新校验课程、发布版本、班级、教师工作区和领取资格，不能只依赖前端传入的 ID；
- 班级授权与课程导入导出是不同能力，课程包文件不能携带班级成员、授权码或学生领取记录。

### 与现有流程的关系

这项想法会影响当前的授权码、领取、学生课程库和课程版本更新流程，但不改变教师 `.kmcourse` 的课程包边界。课程导入导出只负责课程内容迁移；班级授权负责把已发布课程交付给一组学生，二者不能合并成一个文件或一个权限对象。

### 后续进入正式设计前的前置决策

1. 学生是否需要可识别的账号，还是继续只使用本机学习标识；
2. 班级花名册由老师手工维护、邀请码加入，还是由其它教务系统同步；
3. 老师代学生操作的最小权限和学生确认机制；
4. 班级授权码的可复用性、人数上限、有效期和撤销模型；
5. 学生已安装课程与班级状态变化之间的关系；
6. 班级功能是否属于教师自助能力，还是初期仍需管理员配置。
