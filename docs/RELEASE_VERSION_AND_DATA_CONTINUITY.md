# 正式发布版本与数据连续性说明

状态：提议作为下一次正式发布前的项目基线

更新时间：2026-09-01

## 1. 目的

KnownMap 已经从单纯的本地开发系统进入需要长期保留账号、课程、草稿、发布版本、授权记录和资源文件的阶段。
从下一次正式发布开始，不能只看“代码有没有 push”，也不能用重新建库或删除旧数据来解决版本不一致。

本说明定义发布时必须同时关注的版本、数据和证据。它不替代具体需求、契约或 Alembic migration；它负责把这些真源
放到同一条可追溯的发布链上。

## 2. 五种版本不能混成一个数字

正式发布需要同时记录以下身份。它们之间有关联，但职责不同，不能互相替代。

| 身份 | 含义 | 真源或证据 | 是否可以单独变化 |
| --- | --- | --- | --- |
| 产品正式版本 | 用户理解的产品版本，使用 `MAJOR.MINOR.PATCH` | 下一步应建立根目录 `VERSION` 作为唯一真源 | 可以，但必须在发布记录中声明兼容关系 |
| 代码版本 | 本次运行的精确代码内容 | Git commit SHA；生产标签为 `web-prod/<release-id>` | 每次代码发布都会变化 |
| 插件版本 | Chrome 插件清单和插件行为的版本 | `v1/extension/manifest/targets.ts` 的 `EXTENSION_VERSION` | 可以独立变化；插件一改就必须升级 |
| 数据库版本 | 数据库结构已经迁移到哪里 | 生产库 `alembic_version` 的 Alembic revision | 只允许按已验证 migration 向前迁移 |
| 契约版本 | API、课程包、插件消息和插件存储的兼容版本 | `v1/contracts/versions.json` 及其 Schema | 可以独立变化，但破坏性变化必须协调发布 |

另有一项不属于软件版本的身份：**数据快照/备份身份**。它记录发布前保存的是哪一份生产数据库和资源文件，
用于恢复和审计，不能用产品版本号代替。

### 2.1 产品正式版本

正式版本只表示一组对用户交付的兼容基线，不表示数据库内容版本，也不表示 Git 提交本身。建议采用：

- `MAJOR`：核心流程、数据结构、插件架构或兼容边界不再兼容；需要协调升级或明确迁移；
- `MINOR`：向后兼容的新能力；旧课程、旧账号和旧插件仍应按支持矩阵继续工作；
- `PATCH`：兼容的修复、文案或小范围实现修正。

正式版本真源需要在下一次正式发布前落成一个明确文件或等价的单一配置入口。不能让 README、后端 `0.1.0`、
插件 manifest 和发布标签各自代表“正式版本”。在该真源落地前，`release-id + Git commit` 仍是当前生产发布的唯一
不可变身份，但它不是面向用户的 SemVer 产品版本。

### 2.2 代码版本

代码版本必须使用完整 Git commit SHA 追踪。当前发布脚本已经使用以下形式：

```text
web-prod/<UTC时间>-<commit前12位>
```

一次 Web、API 和插件发布必须来自同一个已经 push 到 GitHub 的 commit。发布记录不得指向工作区未提交的代码，也不得
在记录生成后修改它所记录的源码 commit。

### 2.3 插件版本

插件版本继续沿用项目现有规则：只要改动会进入插件包或改变插件行为，就必须升级 `EXTENSION_VERSION`。发布前必须
同时核对：

1. `EXTENSION_VERSION`；
2. local manifest；
3. production manifest；
4. 最终 ZIP 内的 manifest；
5. 线上下载 ZIP 内的 manifest；
6. 这些产物是否来自同一个代码 commit。

只检查源码或 `manifest.json` 不足以证明插件已发布。旧 ZIP 不能用相同文件名覆盖成“看起来最新”的包而不留下版本和
哈希证据。

### 2.4 数据库版本

数据库版本以生产数据库的 `alembic_version.version_num` 为准，不使用产品版本号代替。每次结构变更必须：

1. 新增一个有明确 `revision` 和 `down_revision` 的 Alembic migration；
2. 在空库上从头执行通过；
3. 在生产数据库副本上执行通过，并确认现有数据数量、关键关系和资源引用没有异常；
4. 评估旧代码是否能读取迁移后的结构；
5. 把迁移前 head、迁移后 head、迁移文件和验证结果写进发布记录。

正式生产阶段默认采用“向前迁移、代码可回滚、数据库不自动降级”的策略。旧代码回滚如果不兼容新结构，不能只切回旧
代码；应先使用兼容修复或经过演练的数据恢复方案。当前 `v1` 也不把数据库降级当作常规能力。

## 3. 数据必须保留什么

正式系统中的以下数据默认属于长期业务数据，发布、重启、普通回滚和插件更新都不能删除或覆盖：

- 管理员、教师、工作空间和账号状态；
- 课程、课节、草稿和课程版本关系；
- 已发布课程快照和课程级授权记录；
- 课程引用的资源文件及其 `assetId`、哈希和 MIME 元数据；
- 操作审计记录和必要的发布/恢复证据。

删除、归档、停用和作废必须是有明确业务语义的操作，不能用“清空数据库后重建”代替。课程发布快照是不可变交付物，
新版本应创建新的发布记录，不应改写学生已经取得的历史快照。

学生插件的本机课程和学习状态不进入服务端数据库备份；它们由插件存储 Schema 和本机恢复策略单独管理。不能因为
服务端回滚成功，就声称学生本机状态也已经恢复。

## 4. 正式发布前的数据处理顺序

正式发布按照下面顺序执行，任何一步的目标环境、数据库或版本身份不明确，都必须停止：

1. **冻结发布身份**：确定产品正式版本、Git commit、插件版本、契约版本和目标环境。
2. **确认数据对象**：确认生产数据库、资源存储、当前 release 和上一个可回滚 release；不得把本地库当作生产库。
3. **创建发布前快照**：备份 SQLite 数据库和课程资源文件，记录时间、来源、范围、大小/哈希和恢复位置。
4. **在副本上迁移**：对备份副本执行 Alembic upgrade，核对 migration head、表结构、关键数据数量、课程发布关系和资源引用。
5. **本机验证精确 commit**：运行适用测试、前端构建、插件构建、最终 ZIP 检查和契约/文档门禁。
6. **提交并 push GitHub**：只允许从已推送的精确 commit 构建发布物。
7. **生产切换**：把代码、Web 产物和插件产物写入不可变 release 目录；生产数据库只执行已经验证过的向前 migration，不覆盖数据库文件。
8. **线上核验**：核对健康、运行时版本、migration head、契约版本、教师端、管理端、公开页面和线上插件下载包。
9. **写入发布记录**：记录所有版本身份、数据库迁移前后 head、备份身份、产物哈希、验证范围和剩余风险。
10. **保留回滚路径**：保留上一个代码 release、发布前数据库/资源快照和明确的恢复步骤；回滚后重新执行健康和数据一致性检查。

## 5. 数据库变更的安全模式

涉及生产数据的结构变更默认使用 `expand -> migrate -> contract`：

1. **Expand**：先增加可兼容的新字段、表或索引，不删除旧字段；旧代码仍能运行。
2. **Migrate**：备份后分批或可恢复地填充数据，检查数量、唯一性、外键关系和业务对象完整性。
3. **Contract**：确认所有生产代码和发布物不再依赖旧结构后，才在单独发布中评估移除旧字段或旧路径。

禁止在普通发布中直接执行以下操作：清空业务表、覆盖生产 SQLite、无备份删除字段、改变已有 ID 的含义、重置已有
教师密码、把本地测试数据推回生产，或用插件更新顺便清理学生本机课程。

## 6. 发布记录必须回答的问题

每一份 `deploy/releases/<release-id>.json` 或其后续等价记录，至少要能回答：

| 问题 | 必须记录 |
| --- | --- |
| 发布了什么代码？ | 产品版本、完整 Git commit、GitHub 分支/标签、release-id |
| 发布了什么插件？ | 插件版本、目标（local/production）、ZIP 哈希、下载地址和 manifest 版本 |
| 数据库处于什么状态？ | 迁移前 head、迁移后 head、是否执行 migration、执行目标 |
| 数据是否安全？ | 备份/快照 ID、数据库和资源范围、完整性检查结果 |
| 兼容性如何？ | API、课程包、消息、插件存储版本和支持矩阵 |
| 如何恢复？ | 上一个代码 release、数据恢复点、是否需要 forward-fix、负责人/操作入口 |
| 哪些没有验证？ | 未执行的测试、未确认的生产数据、剩余风险和阻止条件 |

发布记录中不得保存密码、Cookie、私钥、授权码原文、会话令牌或生产环境变量。

## 8. 本说明本次不做的事

- 不因为新增这份说明而升级产品版本、插件版本或数据库版本；
- 不修改生产数据库，不执行 Alembic migration，不删除或重建课程数据；
- 不把当前后端 `0.1.0`、契约清单 `1.0.0` 或 Git release-id 强行改成同一个数字；
- 不把“代码已 push”表述成“数据已备份”或“生产已发布”；
- 不把现有早期发布流程默认为正式生产数据治理已经完成。

正式发布前，按本说明冻结版本真源和发布记录字段，再单独修改 `tools/release.sh`、备份/恢复检查和相关自动化测试。
