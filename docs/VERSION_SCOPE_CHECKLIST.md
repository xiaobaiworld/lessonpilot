# 版本范围与兼容性清单

## 目的

新版本发布前，必须先说明它和上一版本的关系。新增功能不等于可以重写并删掉旧功能；如果确实要替换或移除，必须把范围、原因和迁移方式写清楚。

本清单适用于插件、课程运行时、教师端和学生端等用户可见的版本更新。

## 一、先确定版本类型

每次开发开始前，先选择一种类型，并写明兼容基线：

- **叠加功能**：保留原有行为，只增加新能力。
- **兼容改造**：内部实现可以变化，但用户可见能力、入口和数据兼容性必须保留。
- **替换迁移**：新系统替代旧系统，必须提供完整的功能对照、迁移方案和回滚方案。
- **功能移除**：明确删除某项能力，必须说明原因、用户影响、替代方案，并经过确认。

默认按“叠加功能”或“兼容改造”处理。没有明确写入移除清单的旧功能，一律视为必须保留。

## 一点五、插件一改就必须自动升级版本号

这是项目强制定义，不是提醒项：只要学生插件发生改动，就必须自动更新插件版本号，不等待用户再次提出。凡是会进入插件包或改变插件行为的内容都算插件改动，包括 `v1/extension/` 下的运行时代码、弹窗、设置页、背景脚本、内容脚本、清单、权限、内置图片/音频、资源清单、构建配置和打包清单。开发开始时先读取当前已发布版本，再按本次功能影响范围选择新版本号。插件清单使用三段式版本号 `主版本.次版本.补丁版本`。

插件版本唯一真源是 `v1/extension/manifest/targets.ts` 的 `EXTENSION_VERSION`。`manifest.json` 由构建生成，`v1/package.json` 的 `0.0.0` 只是工作区版本，不代表插件版本。不得用旧版本号覆盖新插件包，也不得把版本判断留给用户补充。

| 功能规模 | 版本变化 | 判断标准 | 示例 |
| --- | --- | --- | --- |
| 小功能 | `0.0.1` | 单个小入口、文案、局部交互、单个资源或不改变整体流程的小修正 | `1.2.0` → `1.2.1` |
| 大一些的功能 | `0.1` | 一个完整功能模块、一个新的用户流程，或需要跨多个文件但保持主架构兼容 | `1.2.0` → `1.3.0` |
| 大版本 | `1.x` | 核心产品流程、数据结构、插件架构或多个主要模块发生整体升级 | `1.2.0` → `2.0.0` |

执行规则：

1. 只要插件包输入或插件行为发生变化，版本号就必须由开发范围自动判断并升级，不能继续使用原版本号覆盖新插件包。
2. 如果一次改动同时符合多个等级，按较高等级升级。
3. 仅修改文档、设计草稿或只影响测试且不进入插件包的内容，不升级插件版本号；只要同时修改了插件包输入或插件行为，仍必须升级。
4. 当前插件发布基线为 `1.2.0`；例如新增学生账号注册登录，如果只增加独立入口且不改课程主链路，默认按大一些的功能处理为 `1.3.0`，若同时改变课程存储、同步和登录架构，则升级为 `2.0.0`。
5. 每次版本判断仍必须填写本清单中的“版本范围记录”、功能基线和验证范围，版本升级不能替代兼容性检查。
6. 发布前必须核对 `EXTENSION_VERSION`、local/production 两套 manifest、最终 ZIP 和线上下载包版本一致；发现插件输入已变更而版本未变更时，停止发布并先修正版本。

## 二、版本范围记录

开发任务或发布记录中必须填写：

| 项目 | 内容 |
| --- | --- |
| 上一版本 | 版本号、分支或提交号 |
| 新版本 | 版本号、分支或提交号 |
| 发布版本标识 | 插件版本号必须和上一发布不同，并记录对应提交号或发布号 |
| 版本类型 | 叠加功能 / 兼容改造 / 替换迁移 / 功能移除 |
| 用户可见目标 | 这次更新解决什么问题 |
| 必须保留 | 原版本不能消失的功能 |
| 有意修改 | 行为、界面或交互发生了什么变化 |
| 明确移除 | 哪些原功能不再保留，以及原因 |
| 本次验证范围 | 插件 / 页面 / 单个模块 / 跨模块 / 全量，以及选择理由 |
| 迁移与回滚 | 用户如何继续使用，出现问题如何恢复 |

“明确移除”不能留空后默认删除。没有移除项时填写“无”。

## 三、发布版本必须唯一

对外发布插件时，每次发布都必须生成一个新的、可区分的插件版本号，不能用同一个版本号覆盖旧 ZIP。通常按补丁版本递增，例如 `1.0.2` 之后发布为 `1.0.3`。

同时记录以下信息：

- 插件包内的 `manifest.json` 版本号。
- 对应的 Git 提交号或远程发布号。
- 线上下载链接实际指向的包。
- 旧版本是否仍可回滚或下载。

同一个下载文件名可以继续作为“当前最新版”入口，但文件内容和包内版本必须已经更新；必要时还要通过发布号或响应校验确认没有缓存旧包。

## 四、功能基线矩阵

新版本必须逐项对照上一版本。每一行都要有自动化证据或手工验证记录。

| 功能或入口 | 上一版本行为 | 决策 | 新版本实现位置 | 自动化证据 | 手工证据 |
| --- | --- | --- | --- | --- | --- |
| 品牌图标与清单图标引用 |  | 保留 / 修改 / 移除 |  |  |  |
| 弹窗入口与插件下载入口 |  | 保留 / 修改 / 移除 |  |  |  |
| 页面内小人、书包和课程入口 |  | 保留 / 修改 / 移除 |  |  |  |
| 播放控制与原视频/课程模式 |  | 保留 / 修改 / 移除 |  |  |  |
| 课程库、兑换和打开课程 |  | 保留 / 修改 / 移除 |  |  |  |
| 重点提示、选择题、填空题等节点 |  | 保留 / 修改 / 移除 |  |  |  |
| 暂停、确认后继续播放 |  | 保留 / 修改 / 移除 |  |  |  |
| 重播或回退后再次显示节点 |  | 保留 / 修改 / 移除 |  |  |  |
| 学习进度、状态和本地存储 |  | 保留 / 修改 / 移除 |  |  |  |
| 权限、站点范围和消息入口 |  | 保留 / 修改 / 移除 |  |  |  |
| 下载文件、线上链接和版本号 |  | 保留 / 修改 / 移除 |  |  |  |

如果新增功能依赖旧功能，矩阵中必须同时记录两者，不能只记录新增项。

## 五、按影响范围选择验证

全量测试不是每次发布的默认动作。测试范围必须和本次改动的影响范围匹配，在保证风险可控的前提下，优先执行最小必要验证。

| 改动范围 | 必做验证 | 不默认要求 |
| --- | --- | --- |
| 单个函数或单个模块的逻辑修改 | 相关单元测试、相关回归测试；必要时做对应构建检查 | 全项目测试、无关页面测试 |
| 插件功能或插件版本发布 | 插件相关测试、插件构建、最终 ZIP 检查、安装和关键路径冒烟 | 教师端和无关页面的全量测试 |
| 单个页面或页面样式发布 | 该页面测试、页面构建、浏览器冒烟或截图检查 | 插件全量测试、其他页面全量测试 |
| 共享模块、消息协议、数据结构或构建链路修改 | 受影响模块测试、依赖它的产品测试、契约检查 | 只有确认影响全项目时才升级全量 |
| 跨产品、跨目录迁移或架构调整 | 受影响产品的完整回归和必要的全量测试 | 不相关的历史归档内容 |

以下情况才升级为全量检查：修改公共协议或公共数据结构、批量移动或重命名文件、调整打包或发布脚本、同时发布多个产品、修复导致功能丢失的回归事故，或发布记录明确要求全量验证。

“只测改动范围”不等于跳过关键检查：插件发布仍必须检查最终 ZIP，页面发布仍必须确认页面能构建并正常打开，单点逻辑修改仍必须运行直接覆盖它的测试。

## 六、发布前门禁

先根据上一节确定本次验证范围，再执行对应门禁：

1. 检查本次改动范围内的构建、测试和关键用户路径。
2. 只对受影响的入口、资源、权限、消息和线上链接做针对性检查。
3. 插件发布时对比 manifest、最终 ZIP 和下载链接；页面发布时验证页面构建和打开；单点逻辑修改时验证直接依赖它的测试。
4. 只有触发全量条件时，才执行全项目测试和跨产品验证。
5. 在发布记录中写明：验证范围、选择理由、执行的测试、未执行的测试和剩余风险。
6. 只有在“明确移除”经过确认后，才允许从包或代码中删除对应功能。

对于插件，至少要检查最终 ZIP，而不是只检查源码：manifest 引用的图标必须存在，关键脚本和资源必须进入 ZIP，线上下载链接必须指向本次发布版本。

## 七、这次事故的记录

2026-08-24，V1 `1.0.1` 被错误地当成了完整替换版本，实际只保留了最小运行链路，导致原有图标、学生助手小人、书包课程入口、播放控制和相关用户路径消失。后续 `1.0.2` 按功能基线恢复了这些能力。

结论：版本号变大不代表旧功能可以消失；测试也不应无差别扩大范围。以后每次做新版本，都必须先回答“改了什么、哪些必须保留、哪些明确移除、应该测到哪里”，再开始改代码和发布。
