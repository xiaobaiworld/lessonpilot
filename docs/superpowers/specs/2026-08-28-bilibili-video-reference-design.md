# B 站课程视频引用与分 P 精确匹配设计

- 日期：2026-08-28
- 状态：已确认，进入实现
- 关联决策：`D-V1-021`
- 关联需求：`FR-RUNTIME-002`、`FR-RUNTIME-013`、`FR-RUNTIME-014`、`FR-LIB-014`

## 1. 本轮结论

课程绑定对象不是单独的 BVID，而是“B 站视频 + 具体分 P”的完整视频引用。第一阶段统一使用：

```json
{
  "platform": "bilibili",
  "videoId": "BV1bDoLYVE1k",
  "page": 4,
  "cid": null
}
```

其中：

- `videoId` 是 BVID，标识整条投稿；
- `page` 是 1 开始的分 P 编号，对应 URL 查询参数 `p`；没有 `p` 时规范化为 `1`；
- `cid` 是 B 站内容 ID。它是可选的更强身份；已知时运行时必须优先按 `cid` 精确匹配；
- `vd_source`、`from_spmid`、`spm_id_from` 等来源追踪参数不参与课程身份匹配，也不写入课程业务对象。

## 2. 示例 URL 的解析

给定：

`https://www.bilibili.com/video/BV1bDoLYVE1k/?p=4&vd_source=e7c7f9591fda9ac995d213b1cf10137c`

规范化结果为：

```text
platform = bilibili
videoId  = BV1bDoLYVE1k
page     = 4
cid      = 未提供
```

`vd_source` 只用于 B 站的来源/归因链路，不能用来区分课程分 P，也不能作为插件显示条件。它在课程编辑、课程包、插件存储和运行时比较中全部忽略。

## 3. 参数分类

| 参数/路径 | 类型 | 业务含义 | 是否进入匹配键 | 处理规则 |
| --- | --- | --- | --- | --- |
| `/video/BV...` | 路径 | 投稿 BVID | 是 | 必须解析为合法 BVID |
| `p` | 查询参数 | 分 P 编号，1 开始 | 是 | 缺省为 1；非正整数拒绝，不静默回退 |
| `cid` | 查询参数 | UGC 内容 ID | 是 | 已知时优先于 `p`；只接受十进制数字 |
| `aid` | 查询参数/播放器参数 | AV 号 | 第一阶段否 | 不在本轮从 AV 解析 BVID，避免产生不确定映射 |
| `bvid` | 播放器参数 | BVID 的另一种传递方式 | 第一阶段否 | 只作为外部播放器协议参考，不替代页面路径 |
| `t` | 查询参数/播放器参数 | 从第几秒开始播放 | 否 | 不影响课程属于哪一 P；由播放器自行处理 |
| `vd_source` | 查询参数 | 来源/归因标识 | 否 | 全部忽略 |
| `spm_id_from`、`from_spmid` 等 | 查询参数 | 页面来源追踪 | 否 | 全部忽略 |
| 其它未知参数 | 查询参数 | B 站页面或营销扩展参数 | 否 | 不影响匹配，但不保存到业务对象 |

官方播放器协议将 `p` 定义为从 1 开始的分 P，将 `cid` 定义为 UGC 内容 ID；当播放器直接给出 `cid` 时，`p` 不再是播放器选择内容的依据。本项目因此把 `cid` 作为更强的规范化身份，但仍保存规范化后的 `page` 供教师理解和无 `cid` 页面匹配。

参考：

- [Bilibili Player 外部嵌入参数说明](https://player.bilibili.com/)
- [B 站关于 `vd_source` 的公开讨论记录](https://github.com/the1812/Bilibili-Evolved/discussions/3424)

## 4. 精确匹配规则

匹配键按以下顺序确定：

1. `videoId` 不同：不匹配；
2. 两边都有 `cid`：只有 `cid` 相同才匹配；
3. 任意一边有 `cid`、另一边没有：不匹配，不降级到 `page`；
4. 两边都没有 `cid`：只有 `page` 相同才匹配；
5. `vd_source` 和其它追踪参数即使不同，也不影响匹配。

因此，同一 BVID 的 `p=1` 和 `p=4` 是两个不同课程绑定对象；教师把第 4 P 绑定到课程后，学生打开第 1 P 不得显示该课程 UI。

## 5. 第一阶段边界

第一阶段接受 B 站直接视频页面的 BVID 路径，并解析 `p`、`cid`。短链、AV 号、番剧、合集和直播链接暂不猜测其对应的课程对象；如果没有经过明确解析，教师端应拒绝保存，而插件端应保持静默。

插件的 manifest 可以继续在 B 站视频页面注入内容脚本，但“注入”不等于“显示”：只有完整视频引用找到精确课程候选后，才挂载陪伴 UI 和学习窗口。非课程视频、其它分 P 和离开视频页都必须清理 UI。

## 6. 数据结构变更范围

同一语义必须贯穿以下边界，字段名保持一致：

- 教师 API：`video_ref.platform`、`video_ref.video_id`、`video_ref.page`、`video_ref.cid`；
- 后端领域/数据库：视频引用增加必填分 P 和可选 CID；
- 课程包：`videoId` 旁增加必填 `page` 和可选 `cid`；
- 插件存储：安装课程的 lesson 引用增加 `page` 和可选 `cid`；
- 插件宿主解析：从当前 URL 产生同样的完整引用；
- 运行时匹配：只比较上述完整引用，不再只比较 BVID。

迁移时旧数据的 `page` 统一填 `1`，旧数据没有 `cid` 不补猜。这样旧课程仍能匹配不带 `p` 的第一页，但不会错误覆盖新的已明确分 P 绑定。

## 7. 防止再次漏检的流程

以后涉及外部 URL 的业务对象，提交前必须有四类证据：

1. **参数分类表**：逐个说明哪些字段是身份、上下文、展示或追踪字段；
2. **单一规范化值对象**：教师输入、后端、课程包、插件运行时共享同一字段语义；
3. **跨边界契约测试**：至少覆盖 URL 解析、保存/读取、课程包序列化、插件匹配的正反例；
4. **真实页面验收矩阵**：同 BVID 不同 `p`、同 `p` 不同追踪参数、无匹配视频、SPA 切换和非视频页都要验证 UI。

测试标题必须写业务对象，而不是只写实现函数。例如使用“第 4 P 不显示第 1 P 课程 UI”，而不是“BVID 匹配成功”。发布门禁要执行这些契约测试和构建产物检查，不能只执行当前模块的单元测试。
