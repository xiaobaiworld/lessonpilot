# 课程互动节点课程化编辑引导设计

- 日期：2026-08-29
- 状态：设计已确认，实现与人工验收完成
- 范围：教师端“编辑交互节点”弹窗及其学生端预览
- 关联决策：[`D-V1-025`](../../../doc/decisions/2026-08-29-course-node-content-guidance.md)

## 1. 背景与目标

当前教师端已经支持重点提示、选择题、填空题和问答题四种互动节点，也已经具备统一的节点编辑弹窗、结构化富文本正文、题型数据和学生端预览。现有编辑器的主要问题不是能力缺失，而是字段表达偏技术化：老师看到的是“页面正文”“解析”“参考答案”等功能字段，不容易快速理解每一栏在课程设计中承担什么作用，也不容易判断应该写什么内容。

本设计的目标是让老师能够在不阅读额外技术文档的情况下完成节点配置：明确这一个节点要教什么、要让学生做什么、学生完成后会看到什么。设计保留现有数据结构和学生端行为，只调整课程化字段名称、分组、占位示例、填写提示、默认标题和编辑器预览文案。

## 2. 已确认的方案与边界

### 2.1 采用方案 A：课程化编辑引导

采用“保留现有数据结构，改善填写引导”的方案：

- 保留节点的 `title`、`content`、`interactionData` 和 `presentationHints` 字段。
- 保留统一的“节点类型 + 触发时间”头部、左侧编辑区、右侧学生端预览和底部保存操作。
- 通过每种节点的课程化标题、字段名称、占位示例和提示语，说明老师当前要完成的教学任务。
- 通过现有富文本能力中的标题、列表和引用表达重点层次，不新增“重点主题”“提醒正文”等独立字段。
- 不新增 HTTP 接口，不变更课程包 schema，不改变学生端判分、完成或播放控制逻辑。

### 2.2 非目标

本轮不做以下事项：

- 不把四种节点拆成四套独立的数据模型。
- 不新增重点提示的独立提醒字段、问答题的独立作答提示字段或其它新的 `interactionData` 字段。
- 不改变学生端窗口尺寸、位置、样式和媒体资源能力。
- 不引入 AI 自动生成题目、选项、答案或反馈。
- 不修改销售页和其它不属于当前教师节点编辑流程的文案。

## 3. 当前实现事实

当前节点编辑器由以下部分组成：

| 位置 | 当前职责 | 本轮影响 |
| --- | --- | --- |
| `v1/web/teacher/src/components/NodeForm.tsx` | 编辑标题、富文本正文、题型数据和学生端预览 | 主要修改：课程化字段文案、分组、提示和预览标签 |
| `v1/web/teacher/src/nodes.ts` | 节点元数据、默认节点、类型切换和本地必填检查 | 修改节点标签、默认标题和错误字段名称 |
| `v1/web/teacher/src/pages/LessonPage.tsx` | 节点弹窗外壳、类型/时间、保存和删除 | 保持弹窗流程不变，仅确认错误提示仍能承接新字段名 |
| `v1/web/teacher/src/index.css` | 节点弹窗、字段、选择题选项和预览样式 | 只在新增分组提示需要视觉承载时做最小样式调整 |
| `v1/extension/content/window.ts` | 学生端窗口渲染、作答和结果反馈 | 不修改行为；继续消费相同字段 |
| `v1/contracts/` | 课程包和消息契约 | 不修改 schema |

现有字段映射如下：

| 节点类型 | 学生主要内容 | 题型数据 | 本轮语义化后的课程任务 |
| --- | --- | --- | --- |
| `notice` | `title` + `content` | `null` | 让学生记住本节此刻的重点 |
| `choice` | `title` + `content` + 选项 | `options`、`answer`、`explanation` | 通过选项检查学生是否抓住判断依据 |
| `blank` | `title` + `content` + 输入框 | `acceptedAnswers`、`normalize`、`explanation` | 让学生补出课程关键词 |
| `free_text` | `title` + `content` + 输入框 | `referenceFeedback` | 让学生把理解用自己的话说出来 |

## 4. 四种节点的编辑规范

### 4.1 重点提示

教师端字段：

- 节点类型标签：`重点提示`。
- 默认标题：`本节重点`。
- 标题字段：`重点主题`。
- 富文本字段：`重点内容`。
- 区块说明：`告诉学生这一刻要理解或记住什么`。
- 填写提示：`建议先写清结论，再补充必要解释；可以用小标题、列表或引用整理层次。`
- 富文本占位示例：`例如：回答问题时，先给出清晰结论，再用具体经历和结果证明。`

重点提示不新增独立的“提醒”字段。需要表达行动提醒时，老师在现有富文本正文中使用引用或单独的小标题，例如：

```text
重点：回答问题时先说结论。

说明：再用具体经历和结果证明这个结论。

提醒：不要一上来铺陈背景，让对方等你的观点。
```

学生端预览标签使用 `本节重点`，正文仍按 `RichPageDocument` 原样预览。保存前仍只要求标题和富文本正文非空。

### 4.2 选择题

教师端字段：

- 默认标题：`想一想`。
- 标题字段：`题目名称`。
- 富文本字段：`题目主干`。
- 区块说明：`提出一个需要学生判断的问题`。
- 填写提示：`题干只提出问题，不要把正确答案或答案提示写进去。`
- 选项区标题：`请手工填写选项`。
- 选项行文案：`选项 1`、`选项 2`、`选项 3`……
- 正确答案操作提示：`标记为正确答案`。
- 反馈字段：`学生作答后的解释`。
- 反馈提示：`答对或答错后，学生都会看到这段解释，然后继续学习。`

编辑完成后的信息顺序必须清楚对应：

```text
题目主干 → 选项 1 / 2 / 3 → 标记正确答案 → 学生作答后的解释
```

保留当前至少 2 个、最多 6 个选项的边界；选项仍由老师手工输入，正确答案仍通过现有单选控件标记。学生端仍使用单选、提交、确定性判断和解释反馈。

### 4.3 填空题

教师端字段：

- 默认标题：`补全关键词`。
- 富文本字段：`题目主干`。
- 区块说明：`让学生补出这一段课程中的关键表达`。
- 填写提示：`请在需要学生填写的位置使用 ______，不要把答案直接写进空格。`
- 答案字段：`标准答案 / 可接受说法`。
- 答案提示：`多个说法用 | 分隔，例如：结论 | 明确结论 | 清晰结论。`
- 反馈字段：`学生提交后的解释`。

现有 `acceptedAnswers` 和 `normalize` 规则不变。学生仍输入一个答案，提交后按原有规则匹配并看到解释。

### 4.4 问答题

教师端字段：

- 默认标题：`说说你的理解`。
- 富文本字段：`问题`。
- 区块说明：`让学生结合课程内容说出自己的理解`。
- 填写提示：`问题应能让学生联系刚刚学到的内容，而不是只回答“是”或“不是”。`
- 反馈字段：`学生提交后的参考反馈`。
- 反馈提示：`学生提交后展示；不自动判分。`

本轮不新增独立的“作答提示”字段。若需要提示，老师可以把提示写在“问题”富文本正文中，或用正文中的列表/引用组织要求。学生仍提交自由文本并看到 `referenceFeedback`，不产生自动正确结论。

## 5. 交互与数据流

### 5.1 编辑流程

```text
选择节点类型
  -> 显示该类型的课程化填写任务
  -> 老师填写标题/正文/题型数据
  -> 右侧预览实时反映同一份草稿节点
  -> 保存前执行现有本地必填检查
  -> 写入现有 ScriptNode
```

节点类型切换继续沿用现有规则：稳定 `id`、时间锚点、标题（若非空）、正文和展示提示保留；旧类型的无效题型数据不迁移。类型切换不新增兼容层，也不自动改写老师已经输入的正文。

### 5.2 学生行为

| 类型 | 打开后 | 提交/确认 | 结果 |
| --- | --- | --- | --- |
| 重点提示 | 阅读正文 | `确认并继续` | `acknowledged`，继续播放 |
| 选择题 | 选择一个选项 | `提交` | 按 `answer` 判断并展示解释 |
| 填空题 | 输入答案 | `提交` | 按 `acceptedAnswers` 和 `normalize` 判断并展示解释 |
| 问答题 | 输入自由回答 | `提交` | 展示 `referenceFeedback`，不自动判分 |

本轮只重写教师端的理解入口和预览说明，不改变上述行为、结果状态、播放恢复时机或本机学习状态。

## 6. 错误提示与状态

保存前继续阻止不完整节点进入草稿：

- 标题为空：提示 `节点标题`。
- `notice` 正文为空：提示 `重点内容`。
- `choice` 正文为空：提示 `题目主干`。
- `choice` 有空选项：提示 `选项文字`；没有正确答案：提示 `正确答案`；没有反馈：提示 `学生作答后的解释`。
- `blank` 正文为空：提示 `题目主干`；没有可接受答案：提示 `标准答案 / 可接受说法`；没有反馈：提示 `学生提交后的解释`。
- `free_text` 正文为空：提示 `问题`；没有反馈：提示 `学生提交后的参考反馈`。

本地检查仍然只做非空和已有结构的最低检查，后端仍是最终校验方。后端错误字段如果仍返回底层字段名，教师端不改变错误真实性，不通过删除或改写数据来“修复”校验失败。

## 7. 视觉与布局原则

- 保留现有节点弹窗的左右结构：左侧填写，右侧预览。
- 每个节点类型的编辑区先出现“这一栏要完成的课程任务”，再出现字段。
- 题型数据与正文之间使用清晰的区块标题和短提示，不把所有字段堆成连续的技术表单。
- 占位示例使用课程语境中的完整句子，而不是 `请输入内容` 这类空泛文本。
- 选择题选项行必须让“填写选项”和“标记正确答案”同时可见，避免老师需要猜单选按钮用途。
- 预览展示真实标题、正文、选项和输入控件；空内容只显示明确的教学占位，不伪造已完成内容。
- 保持现有响应式行为：桌面端左右栏，窄屏时上下排列，页面和弹窗不产生额外横向溢出。

## 8. 实现边界与文件影响

预计实现集中在教师端：

1. 在 `NodeForm.tsx` 中为四种节点整理课程化 copy，给 `Field`/`Area` 增加必要的 placeholder/hint 承载，并重命名题型区块。
2. 在 `nodes.ts` 中更新 `NodeMeta` 的重点节点标签、4 种默认标题和保存前错误字段名称。
3. 根据实际渲染结果，在 `index.css` 做最小的区块标题/提示样式调整；如果现有样式足够，则不新增样式。
4. 补充教师端组件/模型可验证的测试，覆盖默认标题、节点类型标签、本地错误字段名称和选择题字段顺序；保留现有节点结构测试。
5. 运行教师端测试、类型检查、构建和项目级契约/文档检查，确认没有触碰课程包 schema 或学生端行为。

不修改 `v1/extension/content/window.ts` 和 `v1/contracts/`，除非验证发现当前预览或现有标签在实际学生端存在与本设计直接相关的回归；若需要超出教师端的改动，必须重新说明影响并重新确认范围。

## 9. 验收标准

### 9.1 老师填写理解

- 打开任一节点编辑弹窗后，老师能从区块标题和提示中判断这一栏的课程目的。
- 4 种节点都不再把正文、解析和参考答案单独呈现为难以理解的技术字段。
- 选择题的填写路径能明确呈现“题目主干 → 手工输入选项 → 标记正确答案 → 作答后解释”。
- 填空题能明确呈现题干、答案范围和提交后的解释。
- 问答题能明确区分要问学生的问题与提交后的老师反馈。
- 重点提示能通过现有富文本的标题、列表和引用表达重点层次，无需新增字段。

### 9.2 保存与预览

- 空标题、空正文、空选项、未标记答案和空反馈仍会被阻止保存，且错误字段名称使用课程化文案。
- 预览中的标题、正文、选项和输入控件与当前节点草稿同步。
- 节点类型切换仍保留稳定 id、时间锚点、正文和展示提示，不携带旧类型的无效题型数据。
- 保存并刷新后，节点内容和展示设置保持不变。

### 9.3 回归

- 现有 4 种节点的结构测试通过。
- 学生端重点提示确认、选择题判分、填空题答案匹配和问答题参考反馈测试通过。
- `npm --prefix v1 test`、`npm --prefix v1 run type-check` 和 `npm --prefix v1 run build` 通过。
- 项目级 `npm test`、`npm run check` 按当前发布门禁执行；未因本轮 UI 文案变化而新增契约字段。

## 10. 未决与重开条件

当前没有阻塞实现的未决项。以下情况出现时，才重新评估是否从方案 A 升级为新增结构化字段的方案 B：

- 老师需要单独查询、排序或复用“重点主题”“行动提醒”等内容；
- 学生端需要对重点内容的不同区块采用不同的程序化布局或完成规则；
- 课程包、后端或其它客户端需要独立消费这些区块；
- 真实试用反馈证明仅靠字段文案和富文本提示仍不足以让老师正确完成配置。

在上述条件出现前，不新增字段，不让 UI 设计提前扩大公共数据契约。
